## 變更摘要 (WHAT)

- 新增 `api/realtime/inventory_monitor.py`：asyncio 定期 loop（預設 60s）
- `_alerted` in-memory set 防止重複轟炸 — 只對「新進入低水位」推 WS
- 補貨恢復後從 set 移除，下次再低水位時會再推
- FastAPI lifespan 啟動 / 停止 monitor
- payload 對齊前端：`{type: "low_stock", payload: {part_id, part_number, name, current_stock, threshold}}`

## 背景與動機 (WHY)

`/realtime/inventory/low-stock` 通道從 v1.20.0 起就在 server，前端 v1.15.0 已訂閱，但一直無觸發。本次補完最後一個 WS 通道的 server-side 觸發（RBAC 除外）。

## 影響評估 (IMPACT)

- 後端 routes 不變（背景任務）
- 限制：
  - 單機 in-memory `_alerted`（多 worker 部署需 distributed scheduler / Redis Lock）
  - inventory_items 沒 tenant_id，不分 tenant 推送
- 環境變數：`INVENTORY_MONITOR_INTERVAL_SECONDS`（預設 60，最小 10）
- 完成度：總體 92% → **93%**

## 驗證方式

### 自動化
- ✅ 後端載入成功（123 routes）
- ✅ `_scan_once` 邏輯獨立測試通過

### 手動驗證

```bash
cd api && uvicorn main:app --reload --port 8001
# 終端會看到 log: "InventoryMonitor started (interval=60s)"
```

| 步驟 | 預期 |
|:---|:---|
| 啟動後端 | log 顯示 monitor 啟動 |
| 60 秒掃描 | 若有低水位品項 → 推 WS + log「inventory low-stock pushed: N items」 |
| 前端 `/admin/inventory` | 收到 WS 後 4 秒 amber toast + 列表重抓 |
| 補貨後 (UPDATE quantity_on_hand) | 下次掃描從 alerted set 移除（log: "inventory recovered: N items"） |
| 該品項再次低水位 | 再次推送（不會被 dedup 卡住）|

### Manually trigger low-stock for testing

```sql
UPDATE inventory_items
SET quantity_on_hand = 1
WHERE part_number = 'BAT-AA-001';
-- 等 60 秒應收到 WS 推送
```
