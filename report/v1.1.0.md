# 進度報告 v1.1.0：Profile-driven 產品資訊 Loading Gate（Dormakaba 試水溫）

- **版本**: v1.1.0（前版：v1.0.11 → 本版升級類型：MINOR）
- **Commit**: 即將提交
- **分支**: agent-improve
- **作者**: Imding1211
- **影響模組**: agent/product_info（新增）、agent/skills/tools.py、agent/agent.py、agent/harness/debounce.py、agent/prompts/system.md

## 變更摘要 (WHAT)

- 新增 `agent/product_info/` 知識架構：每個 (品牌, 型號) 一份 self-contained mega-doc，本期共 16 份 Dormakaba 型號文件 + 4 份 `_common/*` 通用文件
- 新增 `load_product_info` tool，依用戶 profile 嚴格 gating：品牌+型號齊備才能載入該型號文件，否則僅能載入 `_common/*`
- `debounce.py` 注入點分流：Dormakaba 用戶看 `[可用產品資料]`，其他品牌維持舊 `[可用技能]` 流程
- Checkpoint cleanup 與 audit log 同步支援新 tool
- system prompt 新增「知識來源」「手冊連結處理」兩段，明確區分 `load_product_info` vs `load_skill` 適用情境

## 背景與動機 (WHY)

舊架構 67 份分散 SKILL.md 由 LLM 透過 `load_skill` 動態載入，痛點：
- 資料散，ts-/app-/ss- 切多份，LLM 在多候選中誤判 → 答錯
- `load_skill` 的品牌/型號 gating 不夠嚴格

新方向把「LLM 自由挑選」改成「profile 限縮可選範圍 + 一份 mega-doc 涵蓋全部該型號知識」。Dormakaba 試水溫驗證流程後，再決定是否擴展。

業主強調：所有新內容必須**只從 `data/storage/bronze/`** 整理，禁止從既有 `agent/skills/data/` 二次處理（避免繼承舊架構混亂）。GDrive PDF 內容業主判斷不完全正確，**只放連結不引用內容**。

## 影響評估 (IMPACT)

- **破壞性變更**：無。`load_skill` 與全部 67 份 SKILL.md 完整保留，其他品牌（Chatlock/3E/Philips/Kaadas/Milre/AiLock）流程不變
- **僅 Dormakaba 用戶會走新流程**：profile 中 `device_brand=Dormakaba` 觸發，新增工具 `load_product_info` 可被 LLM 調用
- 後續動作：
  - 試水溫驗證（quality_check + 真機測試）後決定是否擴展其他品牌
  - 若驗證通過，再清理 `agent/skills/data/Dormakaba/` 與 `_common/troubleshoot` 中重複的 Dormakaba 段
  - GL220/ML550/RL320 三型號因無 YouTube 字幕（純 PDF），mega-doc 主要為通用故障 + 手冊連結，需業主決定是否補資料
  - PDF 內容若業主後續驗證可信，可再考慮抽取納入
