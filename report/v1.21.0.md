# 進度報告 v1.21.0：work_order 狀態變化 + refund 決策接通 WS hub

- **版本**: v1.21.0（前版：v1.20.0 → 本版升級類型：MINOR）
- **Commit**: `fecba55` (2026-05-06 00:18)
- **分支**: feat/api-subflow-endpoints
- **作者**: Imding1211
- **影響模組**: `api/services/work_order_service.py`、`api/services/refund_service.py`

## 變更摘要 (WHAT)

- `work_order_service` 新增 `_publish_and_return` helper：fetch 最新 order → publish 到 `/realtime/work-orders/{id}` + `/realtime/dispatch-queue` → return
- 替換 7 個 state-change 函式的 return（accept/complete/cancel/assign/escalate/confirm/reschedule）+ subflow 事件
- `refund_service.submit_decision` 接通 `/realtime/refunds`

## 背景與動機 (WHY)

v1.20.0 上線 WS hub 後僅 schedule resolved 接通；其他 admin 動作（工單狀態 / refund 決策）仍未推 WS，造成多人協作無即時感知。本次補齊。

## 影響評估 (IMPACT)

- 後端 routes 數不變（118）
- 前端不需改：v1.15.0 的 WS 訂閱整合 + v1.15.1 的 dispatch-queue patch state 已能即時消化
- 未接通：disputes（無 decision endpoint）、inventory low-stock（背景偵測 job）、SLA alerts（後端引擎未做）

## 驗證方式

### 自動化
- ✅ 後端載入成功（118 routes）
- ✅ 前端不需改（之前的 build 仍綠）

### 手動端對端
1. 開兩個 admin tab：A `/admin/dispatch-queue`、B `/work-orders/<id>`
2. 在 A 點某工單「指派 / 取消」（或從 dispatch-manual 介入）
3. **預期**：B tab 看到 work_order.{event} 推送 → 工單詳情狀態自動更新
4. dispatch-queue 卡片數字即時 patch（不需 fetchAll）
5. Admin 在 `/admin/refunds` 核准退款 → 同 tenant 任何打開 `/admin/refunds` 的 tab 重抓列表
