## 背景與動機 (WHY)

### 為什麼提前做（即使原列 V1.0 範圍外）

對齊既有「**範圍外提前做基礎設施**」決策模式：

| 同類提前項 | Commit | 為什麼提前 |
|----------|--------|----------|
| 深色模式 | `098caa3` | scaffold + toggle 1 day，等 UX 階段 2 才做反而要重摸 ThemeProvider 設計 |
| 通知 channel 抽象層 | `6ea4802` | 等 V1.5 真接 SMS/Email 時零 refactor，scaffold 1.5 day |
| **i18n scaffold** | 本 PR | 第一個 en 客戶上線前先就位，避免被擋在客戶整合期；漸進遷移近 0 邊際成本 |

### 為什麼 DIY 不裝 next-intl

| 因素 | 評估 |
|------|------|
| 新 npm 依賴 | next-intl 額外 ~30 KB；DIY 0 KB |
| App Router middleware | next-intl 需設定；DIY 不需 |
| URL routing locale (`/zh-TW/...`) | 會破 41 條既有路徑；admin tool 無 SEO 需求 |
| ICU MessageFormat | next-intl 強項；admin labels 99% 不需要複數 / 性別 |
| Hook 形狀 | DIY 對齊 `useTranslations(namespace)` — **未來真要換 next-intl 是 O(provider) 重構，不是 O(callsite)** |
| 漸進採用 | next-intl 強制全頁 namespace；DIY 可 41 頁中只翻 3 頁 |

完整選型矩陣見 [[02-design/specs/i18n-strategy#21-候選比較|i18n-strategy §2.1]]。

### 為什麼鏡像 ThemeProvider 模式

讓未來 reviewer / 新人看到 `LocaleProvider` 時立即理解「這是 theme 模式的 sibling」，不用重學一套。具體對齊維度見 [[02-design/specs/i18n-strategy#4-與-themeprovider-模式對齊|i18n-strategy §4]]：

- localStorage 持久化
- HTML attribute 動態同步（theme: `data-theme`，locale: `lang`）
- Toggle UI 雙變體（icon + segmented）
- 自寫 popover 不裝 dropdown-menu

唯一刻意不對齊的：**沒做 inline FOUC script**。理由：theme 切換閃白會被注意到（RGB 視覺差大）；locale 切換看到 zh-TW 字 ~50ms 才換 en，認知上是「載入完成」而非「閃爍」。Trade-off 決策完整推導在 ADR §4。

### 為什麼 41 頁中只翻 3 頁

V1.0 沒有 en-only 客戶，全量遷移會：

1. 把 ~3-5 dev-day 花在 zero-business-value 工作
2. 維護成本翻倍（每新 key 要動 zh-TW + en 兩份）
3. 字串會 rot（沒人實際用 en，翻譯會逐漸過時）

**漸進遷移策略**：每次動到該頁時順手抽 keys。動到的頁自然就是「在被使用」的頁，rot 風險低。動不到的頁保持硬編 zh-TW，預設語系下零差異。
