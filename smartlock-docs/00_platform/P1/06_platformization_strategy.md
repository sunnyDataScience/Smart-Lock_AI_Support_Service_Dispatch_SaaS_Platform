## 2. 需求拆解

| # | 需求 | 本質 |
|---|---|---|
| A | 模型調用解耦、不依賴任何供應商 | 供應商無關的**模型編排層** |

| C | 新產業時 FDE 只需做：診斷系統(知識核心+model 編排+api 調用效率)、知識庫精煉、工單/金流 flow | **FDE 職責邊界 = 領域配置層** |

## 3. 需求 A — 模型調用供應商無關（Model Orchestration Layer）

現況 agent 已走 LiteLLM（[[ADR-002]]）用 model 字串路由多家，CLAUDE.md 亦硬性禁止 agent code 直接 import 各家 SDK。理想態把它**升格為明確的一層抽象**：

- **供應商 = 配置**（model 字串 + credential），非 code 依賴 → 換供應商零改碼。
- **編排配方 = 配置**：診斷系統的「prompt + skill 行為 + RAG 檢索 + tool 序列 + fallback/eval」是 FDE 可調的**編排配方**，不綁特定家。
- **能力抽象**：路由 / fallback（多供應商容錯）/ eval（OPIK）/ 成本延遲控制 皆供應商中立。
- **API 調用效率**（業主點名）：批次、快取、串流、平行工具呼叫、逾時/重試——屬編排層職責，與供應商解耦。

→ 提案 **ADR-P008：Model Orchestration Layer（供應商無關）**，把 LiteLLM 從「agent 內部細節」抬升為「平台核心的可抽換能力層」，是 FDE 每產業會調、但不需重寫的配置面。

## 4. 需求 B — TRIZ 矛盾解析：抽象化 ↔ 垂直整合

### 4.1 矛盾形式化

**技術矛盾（TC）**
> 若**提升系統通用性/可重用性**（跨產業共用一套核心），則**惡化垂直領域整合深度**（對單一產業的貼合、專用最佳化變淺、複雜度上升）。

- 改善參數 ≈ #35 適應性/通用性（Adaptability / Versatility）
- 惡化參數 ≈ #36 系統複雜度（Complexity）+ 專用功能精度下降

**物理矛盾（PC）**
> 平台**必須同時是通用的**（才能重用）**又是專用的**（才能把藍領垂直做深）。同一個對象需要相反的屬性。

### 4.2 以 TRIZ 分離原則化解 PC

| 分離原則 | 套用到本平台 |
|---|---|
| **按系統層級分離**（最關鍵）| **核心層通用、配置層專用**：把不變的平台原語（工單引擎、agent runtime、金流軌、身分/RBAC、事件骨幹）做通用；把變動的領域邏輯（診斷知識、model 編排、工單/金流 flow）做成**配置/組合**。通用性在核心層、專用性在配置層——**不在同一層競爭**。 |
| **空間分離** | 分層架構：底層通用核心 + 上層領域配置層，物理分開。 |
| **時間分離** | 平台在**設計/build 時是產業無關**的；**專用化發生在「配置/部署時」**（FDE 配置），而非「fork code 時」。 |
| **條件分離** | 同一引擎依「載入哪套 flow 定義 / skill / 編排配方」而表現為不同產業行為。 |

### 4.3 相關發明原則

- **#1 分割（Segmentation）**：工單/金流拆成可組合積木 → 直接支撐需求 D。
- **#2 抽出（Taking Out）**：把「隨產業變」的部分（知識/flow/model 配方）抽離出固定核心。
- **#3 局部品質（Local Quality）**：**垂直深度活在積木裡**——每個積木為其專用功能最佳化。
- **#40 複合（Composite）**：平台 = 固定核心 + 可插拔領域模組。
- **#15 動態化 / #35 參數改變**：flow/積木以配置驅動，改行為不改碼。
- **#25 自服務 / #24 中介**：FDE/客戶經 UI 自行組裝（拖拉）；一層**宣告式 flow DSL** 作為 UI 與引擎的中介。
- **#10 預先作用 / #26 複製**：每產業一套**範本**（藍領服務範本 → 複製 → 微調）。

### 4.4 化解結論（回答業主的擔憂）

> **抽象化「不必然」犧牲垂直整合——前提是把垂直深度從「fork 的 code」搬到「可組合的領域配置（積木＋知識＋flow DSL）」。**

矛盾之所以消解：**「深度」被重定位**——不再是「核心寫死多深」，而是「用多深的領域積木組多細的 flow」。核心保持通用可重用，各產業的深度由組裝深度積木達成，**兩者不再是 trade-off**。

業主擔心的「犧牲整合性」**只有在積木太通用太淺時才會發生**。緩解 = **深度領域積木 + 逃生艙**：
1. 一套**藍領原生**的深度積木庫（派工、技師媒合、到府同意書、施工照/簽名、保固、LINE 溝通、報價核准、對帳結算）——這些積木**本身就垂直很深**。
2. **逃生艙（escape hatch）**：當某產業需要積木庫沒有的邏輯 → 允許自訂 code/plugin 節點，補足 80/20 的長尾。

→ 提案 **ADR-P009：平台核心 vs 領域配置分層**（按系統層級分離，落地 4.2）。

## 5. 需求 C — FDE 職責邊界（分層架構落地）

TRIZ 4.4 的化解直接定義出兩層，**與業主理想完全吻合**：

### 5.1 可重用平台核心（Reusable Platform Core）— FDE 永不動

| 能力 | 元件 |
|---|---|
| 身分 / RBAC / 租戶 / License | Casdoor（[[ADR-P003]]/[[ADR-P006]]）|
| 工單引擎（狀態機執行器）| api 工單核心（把 flow 當**資料**解釋執行）|
| 客服 agent runtime | LockCore（[[ADR-001]]）|
| 金流 / 對帳 / 結算軌 | api 金流核心 |
| 事件 / 即時骨幹 | Kafka / Redis（[[ADR-P007]]）|
| 可觀測性 | SigNoz + OPIK（[[ADR-P002]]）|
| 技師共享池 | technician-platform（[[ADR-P004]]，藍領跨產業共用）|
| 多租戶 provisioning | per-brand bundle（[[ADR-P005]]）|

### 5.2 領域配置層（Domain Configuration Layer）— FDE 每新產業只做這三件

| FDE 工作 | 內容 | 對應核心 |
|---|---|---|
| **① 診斷系統** | 客服知識核心 + model 編排配方 + api 調用效率 | agent runtime + Model Orchestration Layer（A）|
| **② 知識庫精煉** | 該產業的事實語料 + skill 行為 | knowledge-refinery（[[ADR-P001]]）+ RAG-via-MCP（[[ADR-004]]）|
| **③ 工單 / 金流 flow** | 該產業的工單生命週期 + 金流步驟（積木組裝）| 工單引擎 + flow DSL（D）|

> **關鍵**：這三件都是**配置/組裝**，不是改核心 code。新產業上線 = 換一套「診斷腦 + 知識 + flow 定義」，核心原封不動。這就是 TRIZ「按系統層級分離」的具體收益。

## 6. 需求 D — 工單/金流積木化 + 拖拉工作流（可行性評估）

### 6.1 可行性判定

| 面向 | 判定 | 依據 |
|---|---|---|
| flow 編排做成宣告式狀態機/節點圖 | **高可行** | 成熟範式：BPMN/Camunda、Temporal、n8n、ServiceTitan workflow、OpenAI Assistants/AgentBuilder、Retool workflow 皆已驗證 |
| 前端拖拉 = 薄編輯器產出 DSL | **高可行** | 編輯器只是產生/編修 flow 定義，不含執行邏輯 |
| 全 no-code 覆蓋所有垂直細節 | **中** | 長尾需逃生艙（自訂節點），否則會退回「太通用太淺」的陷阱（§4.4）|

### 6.2 設計骨架

1. **Flow Definition DSL**（JSON/宣告式）：`states / transitions / guards / actions`。
2. **工單引擎**把 DSL 當**資料**解釋執行（核心不變、行為隨 DSL 變 = TRIZ 條件分離）。
3. **積木 = 具領域語義的節點型別**：派工、技師媒合、到府同意、施工照/簽名、報價核准、金流收款、對帳結算、通知、escalation、**自訂節點（逃生艙）**。
4. **拖拉 UI**：薄層，輸出/編修 DSL；套用「藍領服務範本」快速起手。

### 6.3 分期（關鍵：別先做編輯器）

- **Phase 1**：工單引擎先**配置驅動**（DSL 解釋的狀態機）——FDE 先手寫/改 DSL。**真正的槓桿在引擎，不在 UI。**
- **Phase 2**：在穩定 DSL 上疊**拖拉編輯器** + 積木庫 + 範本。
- ⚠️ 反面教材：先做華麗拖拉 UI、引擎卻沒抽象化 → UI 產不出引擎能執行的東西。

### 6.4 藍領護城河（為何不是「用 n8n/Zapier 就好」）

通用工作流工具沒有藍領原生語義（到府、實體簽名、施工照存證、保固、技師跨品牌媒合、LINE 客服閉環）。我們的積木**把藍領現實編進節點型別**——這是「ServiceTitan 級快速建置」× 「藍領垂直深度」的差異化。ServiceTitan 綁北美 HVAC/水電生態；我們針對亞洲藍領 + LINE + AI 診斷落地。

→ 提案 **ADR-P010：工單/金流 Flow-as-Blocks（宣告式 DSL + 拖拉編排，分期）**。

## 8. 設計決策鎖定（2026-07-07）

### 8.1 通用工單維運平台三大地基（已裁）

| 決策 | 選定 | 說明 |
|---|---|---|
| 工單領域模型 | 通用核心欄 + JSONB 屬性 + `field_metadata` | 可查詢核心 + 產業彈性欄；欄位語義由 metadata 驅動表單/清單/驗證 |
| 後台呈現 | 共用元件庫 + 每產業組裝（**分兩層**）| **欄位層**配置驅動（`DynamicForm`/`DynamicTable` 吃 metadata）、**畫面層**元件組裝（+ 自訂 panel 逃生艙）|
| 產業配置 | **Vertical Pack 產業包** | 一包 = `field_metadata` + `flow DSL` + `catalog` + `knowledge` + `ui_composition` + `blocks`，版本化 |

### 8.2 FDE 職責邊界（4 配置面，核心不動）

新產業 FDE 只做：**① 診斷系統**（知識核心 + model 編排 + api 調用效率）**② 知識精煉 ③ 工單/金流 flow（DSL）④ 後台 UI 組裝**（元件庫 + 自訂 panel）。平台核心（工單引擎 / 元件庫 / 金流軌 / 身分 RBAC / 事件骨幹）**永不隨產業改**。

## 9. 流程自動化護城河（北極星）

護城河 = **三層複利**，非單一功能：

1. **積木飛輪**：每落地一產業 → 學到新積木 → 進庫；越後面的產業越是既有積木重組，onboarding 越快。
2. **AI Onboarding Compiler**：AI 把客戶 tacit 流程（SOP / 訪談 / 舊系統匯出）**編譯成 flow DSL**，匯入即在 UI 呈現。
3. **Flow = 商業邏輯本體論**：累積的 flow 定義 + 積木庫**編碼各產業營運邏輯** → 資料/本體論護城河 + 轉換成本。

**定位**：平台 = 「**藍領營運的商業邏輯編譯器**」。差異化 = 藍領原生積木本體論 × AI 編譯器 × 累積商業邏輯（n8n / ServiceTitan 只有編輯器）。

**孿生對稱**：AI 流程編譯器 ＝ knowledge-refinery 的流程版——同一 **HITL** 模式（draft → 人審 → commit），一煉知識、一煉流程，共用審核 UI 骨架與 License 附加定位（[[ADR-P011]] / [[ADR-P001]]）。

**三條實作鐵律**：
- **DSL-first**：先定 flow DSL + 積木契約 + 執行引擎（能手寫 / 執行 / 驗證），AI 匯入與拖拉 UI 是疊上去的薄層。順序錯 = AI 產出引擎跑不動。
- **飛輪 bootstrap**：頭 2-3 產業積木**手工建**；庫夠大 AI 命中率才起飛（誠實面對冷啟動）。
- **安全 HITL**：碰金流 / 派工 / 同意書的流程，AI 編出**必過人審**才上線，不盲匯入。
