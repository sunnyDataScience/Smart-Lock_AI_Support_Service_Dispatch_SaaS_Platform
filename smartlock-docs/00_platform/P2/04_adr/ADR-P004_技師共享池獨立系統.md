# ADR-P004: 技師共享池（Technician Platform）獨立系統

| 欄位 | 內容 |
|---|---|
| 狀態 | Accepted（target-state / 理想態 v2）|
| 日期 | 2026-07-07 |
| 決策者 | 業主 + 架構師 |
| 層級 | 平台級（Platform）|
| 關聯缺口 | G-08（跨庫一致性靠雙寫）；解決 per-brand 隔離 vs 共享技師的矛盾 |

## 1. 背景與問題

現況技師身分權威庫 `lock_tech` 為**全品牌共用**（CR-0112），品牌庫留投影靠 api 雙寫 mirror（G-08）。但 target 部署為 **per-brand 物理隔離**（[[ADR-P005]]），兩者衝突：**技師是跨品牌身分**（一個鎖匠可服務多個品牌），不應被切進單一品牌部署。

## 2. 考量的選項

- **選項 A：技師切進各品牌部署** — 違反「技師跨品牌共享」，且同一技師在多品牌重複、無單一真相。
- **選項 B：技師留共享庫但綁在 api（維持雙寫 mirror）** — 延續現況耦合，per-brand 部署下 mirror 更複雜。
- **選項 C：技師獨立成一套系統（共享池），由派工/工單平台串接** — 清晰邊界，技師跨租戶單一真相。

## 3. 決策

採 **選項 C**（業主拍板：「技師應該是獨立共享池，設計上應該是另一套系統，由工單系統平台串接」）：

1. **Technician Platform** 升格為**獨立系統**（跨租戶共享技師池），由現況 `tech-db` / tech-api surface 演進而來。
2. **職責**：技師身分、技能、品牌授權、認證（KYC/certification）、排班、評分、佣金主體；**含獨立師傅 web**（師傅上線註冊 / 工作台 / 技師後台）——師傅端**不放進品牌 bundle**，讓品牌可獨立部署整套單體（[[ADR-P005]]）。
3. **邊界**：各品牌的**派工/工單平台（api）**經 **OHS API + 事件（Kafka）** 串接技師平台（Customer-Supplier / ACL），而非直連技師庫。
4. **收斂雙寫**：以技師平台為單一真相源，品牌側改為經 API 讀取 / 事件訂閱，逐步汰除 mirror 雙寫。

## 4. 後果

**正面**：技師跨品牌共享、單一真相；邊界清晰；per-brand 隔離與共享技師不再矛盾。
**負面/風險**：新增系統邊界 + 跨系統整合成本；派工需經 contract 呼叫技師平台（延遲/可用性依賴）；遷移期需並存雙寫與 API 兩路。
**影響範圍**：新增 `technician-platform/` 系統文件集；api 的技師相關端點改為串接；`lock_tech` 升格為技師平台自有庫。
**重新評估觸發**：若最終只單一品牌營運 → 技師平台可退化為 api 內模組。

## 5. 執行計畫

1. 由 `tech-db` + tech-api surface 抽出 `technician-platform` 獨立服務 + 庫。
2. 定義技師平台 OHS API（技師查詢/媒合/排班）+ 事件契約（技師狀態變更 → Kafka，見 [[ADR-P007]]）。
3. api（派工）改經 ACL adapter 串接技師平台，汰除品牌庫技師 mirror 雙寫。
4. 技師身分認證接 Casdoor（技師為跨租戶身分，見 [[ADR-P003]]、[[ADR-P006]]）。
5. 跨系統契約測試（consumer-driven）。

## 6. 選用影響區段

- **架構**：新增 TechnicianContext 為獨立限界上下文/系統。
- **資料**：`lock_tech` → 技師平台自有庫（單一真相），品牌庫技師改投影/唯讀。
- **整合**：派工 ↔ 技師平台走 OHS API + Kafka 事件。
- **部署**：技師平台為**跨品牌共用元件**（非 per-brand，見 [[ADR-P005]]）。
