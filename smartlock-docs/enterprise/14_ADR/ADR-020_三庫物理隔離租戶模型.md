# ADR-020: 三庫物理隔離的租戶隔離模型

| 欄位 | 內容 |
|---|---|
| 狀態 | Accepted |
| 層級 | 系統級（data）|
| 關聯 ADR | [ADR-002](./ADR-002_per-brand授權部署.md) · [ADR-016](./ADR-016_技師共享池獨立系統.md) · [ADR-017](./ADR-017_技師平台佣金邊界與工單CQRS投影.md) · [ADR-021](./ADR-021_psycopg3_rawSQL與純SQL_migration.md) |

## Context（背景與問題）

多個智慧鎖品牌（Chatlock / Dormakaba / Kaadas…）共用同一套平台，但品牌互為競爭對手，客服、派工、工單、金流資料**必須強隔離**；同時技師身分需跨品牌共用（一個師傅服務多品牌）、平台治理（管理員 / 品牌申請）需獨立於任何品牌。租戶隔離模型必須同時滿足「品牌強隔離」與「技師跨品牌」。

## Decision（決策）

**一品牌一 DB 物理隔離 + 技師庫 + 平台庫（三庫模型）**：

| DB | 實例（範例）| 內容 | 語意 |
|---|---|---|---|
| **品牌庫** | `lock_AI_data`（×N，一品牌一庫）| 全 schema（~100 表，`public` / `saas` / `agent` 三 namespace）| 品牌營運資料物理隔離 |
| **技師庫** | `lock_tech`（:5434）| 技師身分域 6-7 表 | 技師跨品牌**單一真相**（技師平台自有，[ADR-016](./ADR-016_技師共享池獨立系統.md)）|
| **平台庫** | `lock_platform`（:5435）| 獨立 3 表（`users` / `revoked_jti` / `brand_applications`）| 平台治理獨立於品牌 |

- **品牌庫全 schema 每品牌部署一份**（物理多租戶）；fail 模式為 **fail-closed**——連錯庫就是連不到，不會靜默跨租戶洩漏。
- 品牌庫保留技師**投影**（品牌表 FK 指向 `users` / `technicians`，讓派工 / 佣金 JOIN 可行）；投影同步走事件驅動（[ADR-017](./ADR-017_技師平台佣金邊界與工單CQRS投影.md) CQRS），品牌側唯讀。
- 平台庫 `users` 欄位刻意對齊品牌庫 `users` 子集（含帳號安全欄），使 `core/auth.py` lockout 查詢跨庫共用。
- 三庫各有連線 URI（`POSTGRES_URI` / `TECH_POSTGRES_URI` / `PLATFORM_POSTGRES_URI`，[ADR-021](./ADR-021_psycopg3_rawSQL與純SQL_migration.md)）。

## Alternatives（考量的選項）

- **A：一品牌一 DB 物理隔離（採用）** — 隔離最強、fail-closed；代價是部署擴散與跨庫無交易。
- **B：RLS 邏輯隔離（單庫 + `tenant_id` + row policy）** — 省實例，但靠 app 正確設 session，漏設即 fail-open 跨租戶洩漏；競品同庫信任成本高；與技師跨品牌張力大。
- **C：schema-per-tenant（同庫多 schema）** — 中高隔離，但 schema 數線性增長、migration 對每 schema 套、仍是同實例（物理未分）。

## Consequences（後果）

**正面**：品牌資料物理分庫，競品資料不可能同庫洩漏；技師跨品牌與品牌隔離兼顧；平台治理獨立。
**風險**：**部署擴散**——套 migration、備份、監控都乘以品牌數（drift-check CI 見 [ADR-003](./ADR-003_工程治理排程_API收斂_migration_CD.md)）；**跨庫無交易**——技師庫 ↔ 品牌庫一致性走事件 + 對帳閘門（[ADR-017](./ADR-017_技師平台佣金邊界與工單CQRS投影.md)）；連線 URI 配置須有啟動守衛，禁止漏設時靜默退回單庫。
**影響範圍**：`SQL/Schema.sql`、`SQL/platform/Schema_platform.sql`、`scripts/db/*` 三庫腳本、api 三面連線；DB 設計全貌見 [18_DB_Design](../18_DB_Design.md)。
**重評觸發**：品牌數成長到物理分庫成本不可承受 → 重估 schema-per-tenant 或 RLS 補充層。

## Status 附註

- 品牌庫 schema 內保留的 `tenant_id` 欄位為**未來多級隔離的預留欄**，目前不承載隔離語義（隔離完全靠物理分庫）；其去留屬 tier-1 治理事項。
- 🔜 規劃中：三庫 URI 啟動守衛（禁止靜默 fallback）、多庫套用統一入口 + `--verify` 對帳。
- 2026-07-10 稽核：三庫 URI 啟動守衛仍未實作（`api/core/db.py` 靜默 fallback 為既有安全閥；Consequences「須有啟動守衛」與本附註「🔜 規劃中」矛盾，排程歸屬待業主裁決——架構稽核 #6）。
- **2026-07-10 落地（CR-0153，業主裁決採 opt-in）**：`DB_URI_STRICT=1` 啟動守衛——依 API_SURFACE 斷言必要 URI，漏設拒啟；prod deploy 腳本與三站 compose 一律帶上；預設關閉保 pytest／本機單庫 fallback 語意（「須有」與「規劃中」矛盾以此收斂）。
