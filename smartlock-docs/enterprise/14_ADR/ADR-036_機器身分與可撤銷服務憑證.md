## Context（背景與問題）

agent、brand API、technician OHS 與 knowledge-refinery 間已有內部呼叫，現況多使用共用
`X-Internal-Token`。共享長效 secret 缺少每個 workload 的身分、最小 scope、獨立撤銷、
輪替與 last-used 證據；若與真人 Bearer token 混用，更會模糊 audit actor。

OD-001 尚未決定 OHS 最終採 OIDC client-credentials 或受控 internal token；OD-004
尚未決定跨品牌 principal／claim 模型。本 ADR 不越權替兩項 OD 選 transport 或 claim，
先固定兩種選項都必須遵守的機器身分生命週期。

## Decision（決策）

1. **真人與機器分離**：真人使用 OIDC/session；workload 使用 `service_principal`。
   服務不得共用真人帳號，audit actor 必能辨認 workload。
2. **平台 DB 保存 registry**：`service_principal` 定義 owner、purpose、status；
   `service_credential` 定義 key id/prefix、credential hash 或 IdP client reference、
   audience、scope、允許的 brand/tenant scope、expiry、revoked_at、last_used_at、
   rotation generation 與 rate policy。
3. **明文一次性**：若使用 opaque secret，資料庫只存強雜湊；明文只在建立當下顯示一次，
   不進 log、trace、事件 payload 或文件。
4. **最小權限驗證**：每次 internal call 同時檢查 principal active、credential 有效、
   audience、scope、brand scope 與 request id；錯誤一律 fail-closed 並留 audit。
5. **輪替與撤銷**：支援短期 overlap 的雙 credential 輪替、立即撤銷、expiry 與使用量
   監控；撤銷後拒絕延遲需有 SLO。
6. **遷移**：`X-Internal-Token` 僅作有時限 fallback，為每條 caller 加 usage metric；
   caller 遷至 service principal 後，production 使用量歸零才可刪除 fallback。
7. **OD 邊界**：
   - OD-001 若採 OIDC client-credentials，registry 保存 client reference、scope、
     rotation/audit 狀態，runtime 驗證 IdP token。
   - OD-001 若暫留 internal token，也必須符合上述 per-principal hash、scope、expiry、
     revoke、rotate、audit，不能回到全服務共用 secret。
   - OD-004 決定跨品牌 entitlement 的 claim／membership 投影；拍板前不可自行放寬
     `allowed_brand_scope`。

## Alternatives（考量的選項）

- **A：永久共用 `X-Internal-Token`** — 簡單但無法最小撤銷與追蹤，拒絕。
- **B：服務沿用真人 OIDC 帳號** — actor 與責任邊界錯置，拒絕。
- **C：只接受 OIDC client-credentials** — 可能是目標，但會提前關閉 OD-001，現階段不採。
- **D：transport-neutral service principal lifecycle（採用）** — 先固定不可退讓的安全
  屬性，transport 依 OD-001 補新 ADR 定案。

## Consequences（後果）

- ＋任一 workload 可獨立限權、撤銷、輪替與稽核。
- ＋OD-001 無論選哪條 transport，都不會留下永久共用密鑰。
- ＋internal API 可納入 ADR-035 的 BOLA／IDOR 負向契約。
- －平台 DB、管理 API、secret bootstrap 與 audit/metrics 都需新增實作。
- －過渡期間需同時支援舊 token 與新 principal，必須以 telemetry 防止 fallback 常態化。

**完成門檻**：production 無服務共用真人帳號；每條 internal caller 可辨識 principal；
過期、撤銷、錯 audience、錯 scope、跨 brand 均被拒絕；共享 fallback 使用量連續一個
release window 為零。

## 實作與驗證證據（2026-07-27）

- migration 121、`service_credential_service.py` 與 platform-only 管理 router 已實作
  hash-only secret、audience/scope/tenant、expiry、最多 24 小時 rotation overlap、
  revoke、last-used、audit 與建立 action replay 防護。
- `core/deps.py` 先驗新 `X-Service-Credential`，再走有時限 legacy fallback；agent、
  refinery、technician OHS caller 都能使用各自環境變數切換新 credential，且不會在
  新 credential 驗證失敗時降級至 shared token。
- component tests 已覆蓋 secret/hash、錯 hash、expiry、revoke、錯 audience/scope、
  跨 tenant 與 caller 優先序。
- 尚未完成的是外部 production bootstrap、Secret Manager/WIF 配置、OD-001 transport
  定案與 fallback usage 連續一個 release window 為零；在取得該證據前 WBS 3.6.5
  不得標為全數完成。

## 重評觸發

OD-001／OD-004 拍板時，以新 ADR 補 transport 與 claim mapping；不原地把尚未決定的
選項寫成 Accepted。
