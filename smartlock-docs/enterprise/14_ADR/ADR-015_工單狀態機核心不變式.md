# ADR-015: 工單狀態機核心不變式（locksmith flow 首個實例）

| 欄位 | 內容 |
|---|---|
| 狀態 | Accepted |
| 層級 | 系統級（api）|
| 關聯 ADR | [ADR-013](./ADR-013_Flow-as-Blocks宣告式DSL.md) · [ADR-025](./ADR-025_AI話術邊界與永不自轉工單憲章.md) · [ADR-026](./ADR-026_報價快照hash-chain不可否認性.md) |

## Context（背景與問題）

locksmith 工單流程是平台通用工單引擎（[ADR-013](./ADR-013_Flow-as-Blocks宣告式DSL.md)）的首個 flow 實例，其設計須同時達成三個目標：**法律風險防範**（免責 / 個資簽署由客戶本人完成）、**結案 / KPI 依據**（狀態不可隨意改）、**減少現場收費爭議**（費用有來源、可稽核）。若把派工門檻、現場蒐集、法律簽署、計費核銷混在一張「一次填完」的單子上，客服只能瞎猜或留空——序號 / 門厚 / 破壞鎖與否是技師到場才知道的，計費明細是報價 / 完工階段才產生的，簽名只有客戶本人在 LINE 上做得到。

## Decision（決策）

### 狀態轉移鏈

```
問題卡 draft ──確認──▶ created ──派工──▶ assigned ──接單──▶ accepted
    ──▶ in_progress ──▶ completed ──結案 gate──▶（closed）
```

問題卡與工單**分離**：問題卡是診斷 / 分流階段（三層解決：L1 AI 直接回 / L2 遠端指導 / L3 現場派工），**只有 L3 才開單**——工單列表裡每一張都是真的要派車出去的。

### 三條核心不變式

**① WorkOrder.created 硬綁 Quote 客戶確認（含急件 carve-out）**

```
WO.created precondition =
   PC.confirmed
   AND (
     Quote.state = customer_confirmed          -- 標準路徑
     OR pc.emergency_class IS NOT NULL         -- 急件 carve-out
   )
```

- endpoint enforce：`POST /work-orders` 要求 `quote_id`；quote 未確認回 `425 QUOTE_NOT_CUSTOMER_CONFIRMED`、quote 已失效回 `409 QUOTE_STATE_INVALID`。
- **急件 carve-out 四類**（`pc.emergency_class`）：`urgent.locked_out` / `urgent.trapped_inside` / `urgent.safety_risk` / `urgent.angry_high_risk`——跳過 quote 直接開單，**事後 4h 內補 quote audit**（`retrospective_audit_only` → 客戶簽認後 `customer_audit_complete`；4h 未補 → hard alert 通知客服主管）。

**② 結案 422 hard gate（address + quote 雙必驗）**

```
WO 結案 precondition =
   customer_address IS NOT NULL AND length >= MIN_ADDRESS_LENGTH（預設 12，per-locale 可調）
   AND (
     (Quote.customer_confirmed AND pc.emergency_class IS NULL)          -- 標準路徑
     OR (pc.emergency_class IS NOT NULL
         AND retrospective_quote_audit_complete = true)                 -- 急件 + 補 audit 完成
   )
   不符 → 422（error_code: ADDRESS_REQUIRED_BEFORE_CLOSE 等）
```

地址採**三段補**：AI 對話階段最佳努力收集（Quick Reply 追問）→ 派工階段軟性處理（`address = null` 可進 `assigned`，師傅端顯示「地址待補」，師傅已知可標 `address_known_by_locksmith`）→ **結案階段硬 gate**。派工不擋、結案必擋，月結對帳前無漏網。

**③ AI 永不自轉工單（1-click 人審）**

AI 只能草擬問題卡（`source='ai_line'`，經 `POST /internal/escalations/ingest`）；客服在問題卡佇列補全 → confirm → 才呼叫 convert-to-work-order。AI 自身**永不**直接呼叫轉換（憲章鎖死，[ADR-025](./ADR-025_AI話術邊界與永不自轉工單憲章.md)）。開單前另有**完整度 gate**：缺品牌 / 型號 / 症狀 / 急迫度 → 422，需主管填「強制開單原因」override（急修例外逃生門）。

### 漸進式資料蒐集與唯讀規則

- 開單只填最低派工門檻（地址必填 + 聯絡人 / 電話選填）；6 模組資料攤平到生命週期各階段，由「知道它的角色」在「自然產生的那一刻」填。
- **唯讀欄位 = single source of truth**：免責同意（LINE 客戶本人簽，後台代簽無效）、雙方簽認、維修原因（源自問題卡）、完工狀態（完工流程帶入）、費用明細（來自報價，[ADR-026](./ADR-026_報價快照hash-chain不可否認性.md)）。

## Alternatives（考量的選項）

- **軟綁定**（customer_confirmed 為完工前置而非開單前置）— 保住 1-click 開單，但派工後客戶拒絕場景需新增 disputed 狀態 + 取消 reason code，且不符「報價確認才立工單」的業務語義。
- **開單即收齊全部欄位** — 客服瞎猜或留空；免責簽名可被後台代填 = 法律無效。
- **硬綁定 + 急件 carve-out（採用）** — 標準路徑 audit chain 完整、派工後拒絕場景不存在；急件不被綁定阻塞。

## Consequences（後果）

**正面**：地址 / 報價為 schema 級契約而非建議；audit chain 完整（急件也有 4h 補 audit SLA）；垃圾工單被完整度 gate 擋在派工前。
**風險**：客服建單為 2-step（建 quote → 等確認 → 建單）；急件補 audit 為新增客服責任（需 macro / 培訓配套）；`retrospective_quote_audit_complete` 為應用層 422 enforce，非 DB CHECK。
**影響範圍**：`POST /work-orders` 契約、工單 / 報價狀態機、師傅端補地址 UI、BI「無地址工單回填率」儀表板（警示閾值 < 95%）。
**重評觸發**：人審通過率 ≥ 99.5% 且法務 sign-off → 評估低風險場景自動轉單；可信 GPS / LBS 來源出現 → 評估地址自動補填。

## Status 附註

- 本 flow 為 [ADR-013](./ADR-013_Flow-as-Blocks宣告式DSL.md) DSL 引擎的首個驗證實例；不變式①②③ 屬**商業不變式**，任何產業 flow 匯入驗證均不得違反其對應類型。
- `MIN_ADDRESS_LENGTH` 與急件 4h SLA 為可調參數（業主 + 客服主管治理）。
