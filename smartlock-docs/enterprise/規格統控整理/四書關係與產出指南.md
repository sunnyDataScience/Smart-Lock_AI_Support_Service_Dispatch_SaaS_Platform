# Smart Lock Enterprise 規格四書 — 關係與產出指南

> 對象：PM / BA / SA / QA / RD / 架構師<br>
> 一句話：四份 xlsx 是 `enterprise` 正典 Markdown 的單向生成快照；改上游、重跑生成器，不直接維護 xlsx。

## 1. 四書定位

| 書 | 回答的問題 | 主要讀者 |
|:---|:---|:---|
| `SmartLock_規格統控規劃書.xlsx` | 為什麼做、何時做、驗收結果是什麼、已有哪些 ADR、還有哪些契約/追溯風險？ | 經營層 / PM / 架構師 |
| `SmartLock_模組功能BOM.xlsx` | 平台由哪些子系統、能力群與 SRS FR 組成？落在哪個 C4 容器？ | PM / RD / 架構師 |
| `SmartLock_業務邏輯驗收控制表.xlsx` | 客戶 VOC 是什麼？PM 應用什麼 PRD 標準驗收？SA 應看哪個成功指標？ | PM / 業務 Owner / QA / SA |
| `SmartLock_整合測試計畫.xlsx` | QA 如何把 FR/NFR 轉成風險場景、受控測試設計、責任人與執行證據規格？ | QA / RD / SRE |

分工可簡化為：**BOM＝賣什麼，驗收表＝客戶為什麼要、PM 怎樣算通過、SA 要量到什麼，測試計畫＝怎麼證明，規劃書＝什麼時候做與哪些事要先裁定**。

驗收表內的讀者分工：

- `客戶 VOC／商業情境` + `PRD 驗收標準`：PM、BA、業務 Owner 與 UAT 人員。
- `成功指標（架構／SA）`：SA／架構師據以定義量測環境、系統邊界與證據。
- `技術流程對照`：完整保留 04_SRS 的前置／主流，給 SA／RD 回查，不當作客戶 VOC。

## 3. 單一追溯脊椎

```text
BR / PRD 上位需求
        ↓
04_SRS FR/NFR ID ──→ 驗收標準 ──→ QTM ──→ TS 風險場景 ──→ 指定 TC ──→ SIT/UAT 證據
        ↓
     SAD / ADR / API / DB / WBS
```

- 新四書以 `04_SRS` 的 `FR-AGT-* / FR-API-* / ... / FR-PLT-*` 與 `05_NFR` 的 `NFR-*` 為主鍵。
- `AGT·RES`、`API·WO` 等是活頁簿 L2 顯示群，不是新 join key。
- `FR-0001` 形式的編號是既有案例與 `21_Traceability_Matrix.md` 的 legacy 鍵，只作歷史顯示與人工參考；現行 join 已由 `20_Test_Cases.md` §2.1 的 QTM 主表承接。
- 名稱、工作表列號、WBS 與 ADR 都不取代 FR/NFR 主鍵。

## 4. SAD / SDS 元件標籤對照規則

- BOM 的「正式元件名稱」使用 `12_SAD` / `15_SDS` 原文，不再使用 `LockCore runtime / Skills / Memory` 這類無法精確回查的概括詞。
- 每個 FR 會依所屬 L2 能力群投影「正式元件名稱、SAD 定位、SDS 定位、Code reality、實作證據路徑」。需求狀態與程式現況分欄呈現；這是人工架構投影，不是新的 join key。
- 每份活頁簿都有「元件標籤字典」，逐一解釋「是什麼、負責什麼、不負責什麼、從哪裡回查」。
- 同一份可讀的 Markdown 字典見 [SAD / SDS 元件標籤字典](./SAD_SDS元件標籤字典.md)。
- SAD 定位欄連到 `12_SAD.md`（容器層）；SDS 定位欄連到 `15_SDS.md`（詳細元件層）。行號是本次正典快照的輔助座標，章節號才是長期定位。

## 6. 重跑方式

```bash
cd smartlock-docs/enterprise/規格統控整理
python3 _sync_test_canon.py
python3 _build_enterprise_workbooks.py
```

第一步同步 `19_Test_Plan.md` 的場景基線及 `20_Test_Cases.md` 的 QTM 主表；第二步再生四份 xlsx 與 `產出健康報告.md`，並驗證：

- 工作表數與名稱。
- 主表 filter 範圍。
- freeze pane。
- FR/NFR 解析數下限。
- FR 主鍵唯一性、SRS→TC 直接連結與 QA 受控映射健康。
- `19_Test_Plan` 12 個 TS 的名稱、方法與 REQ 數是否和 Excel 一致。
- `20_Test_Cases` 171 筆 QTM 的 REQ、場景、指定 TC、方法、判準及狀態是否逐筆和 Excel 一致。
- L2 能力群是否都有 SAD/SDS 對照。
- BOM 每列 FR 是否都有正式元件、SAD、SDS 與路徑。
- 規劃書「⑧ 完整模組清單」與 BOM 主表 L2 的能力群、FR 數、階段、正式元件、SAD 與 SDS 是否逐列一致。
- 驗收控制表是否具備 VOC、PRD 驗收與成功指標，且 65 列 FR 前置／主流已全數移至技術對照頁。
- 所有架構標籤是否都已在「元件標籤字典」定義，且沒有未使用定義。

## 7. 修改規則

| 想改的內容 | 應修改的真相源 | 不要做的事 |
|:---|:---|:---|
| FR 前置/主流/驗收/追溯 | `../04_SRS.md` | 只改驗收表或 BOM xlsx |
| NFR 門檻/驗證方式/合約分層 | `../05_NFR.md` | 在測試計畫臆造門檻 |
| ADR 狀態與決策 | `../14_ADR/` 新增 ADR 或更新索引 | 修改已 Accepted ADR 的歷史內文 |
| TS/QTM/指定 TC 基線 | `_spec_data.py`、`../04_SRS.md`、`../05_NFR.md`，再執行 `_sync_test_canon.py` | 手改生成標記內的 19/20 主表 |
| 既有詳細 TC 步驟與執行證據 | `../20_Test_Cases.md` 非生成區 / 測試管理系統 | 把 `QTM-*` 設計映射當成已執行證據 |
| Roadmap / WBS / Gate | `../27_Product_Roadmap_WBS.md` | 在規劃書 xlsx 直接改狀態 |
| L2 顯示分群、QA 場景、術語 | `_spec_data.py` | 用顯示代號新建一套追溯鍵 |
| 驗收表的客戶 VOC／PRD 業務語言 | `_spec_data.py` 的 `FR_BUSINESS_COPY` | 把 API／事件／資料庫流程當成 VOC |
| L2→正式元件投影、標籤定義 | `_spec_data.py` 的 `MODULE_ARCH` / `COMPONENT_GLOSSARY` | 在 xlsx 另造未定義縮寫 |
