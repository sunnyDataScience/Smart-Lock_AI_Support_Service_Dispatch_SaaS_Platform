### 五張工作表

| 工作表 | 一列是 | 主要用途 | Plane 邊界 |
|:---|:---|:---|:---|
| `01_需求收斂` | Story | 對焦角色、痛點、價值、FR/NFR 性質、範圍與 owner | `Story` 是唯一直接量測點；`FR/NFR` 映射 `requirement_kind` |
| `02_需求與驗收` | AC 草案 | 以 Given/When/Then 與 NFR 指標定義過／不過 | AC 不另建物件，收進 Story 敘述與 TC 追溯 |

| `04_測試設計` | Test Case | 把 AC 變成前置、資料、步驟與預期結果 | 用 `TestCaseWorkItemLink` M:N 連 Story；Scenario 只是欄位或 tag |
| `05_技術地基` | Enabler | 不掛任何 Story 的技術／品質地基 | 建議掛 `E-GLB` 底下，不掛旅程；不進 Task 層 |

### Task 的定義（2026-08-07 改版）

**一列＝一個 Story 穿過的一個工程層面**，不是一個舊 WBS 工作包。

改版理由是數量關係整個反了：舊版 `03` 一列一個舊 WBS 工作包，**16 列對 171 個 Story**。
Story 拆成 Task 數量只會變多，少一個數量級就代表那張表裝的不是 Task。查證那 16 列也證實：
8 列不掛任何 Story（CD、雲端拓撲、GCP cutover 這種地基），3 列橫跨 ≥2 個 Story（粒度大於
Story，接近 Feature），只有 5 列形狀對得上。它們已移到 `05_技術地基`。

現行拆解規則（`_task_breakdown.py`，共 **173 列 / 65 個 FR Story**）：

- **層面拆解**：資料模型 → API 契約 → 核心邏輯 → 事件 → 授權 → 前端 → 外部整合。
  核心邏輯無條件產一張；其餘層面只有在正典文字命中對應關鍵詞時才產卡，
  **觸發詞與命中的正典欄位寫進「來源追溯」**——規則判錯看得出來，這是它與亂猜的分界。
- **不照 flow 的「→」拆步驟**：65 支 FR 有 35 支的 flow 根本沒有箭頭，而 `FR-AGT-02` 的
  `RESTORE→COMPACT→…→DONE` 是狀態機轉移不是工作分派。照箭頭拆會同時量產假卡。
- **NFR 不逐條產 Task**：106 條 NFR 是跨 Story 的品質地板，依 `_canon.nfr_forms()` 的四種
  驗證形態收斂為 4 張共用 Enabler（一套 k6 骨架服務 45 條門檻量測型 NFR，逐條產只會得到
  106 張重複卡）。
- **完成定義是工程判準**，不等於 TC passed，更不等於業務驗收通過。核心邏輯用 `04_SRS`
  的後置與驗收原文，其餘是層面樣板；欄位標成淺藍 draft 底色，**SD 必須替換成本卡的具體判準**。

> 底色語意：黃＝只有人能填；灰＝生成欄，手改會被覆蓋；**淺藍＝生成器給了草稿但人必須覆寫**；白＝正典敘述。

### 測試情境與測試案例

- **測試情境**回答「在什麼狀況下驗」，不是 Plane 物件，也不是舊 SC/TS/UAT 改名。
- **測試案例**回答「這一次具體怎麼驗」，必須有前置、資料、步驟與預期結果。
- 路徑類型只有 `happy / boundary / failure / recovery`；「驗什麼」另用驗證面向欄位表達。

## 0. 這套規格對應的正統語彙（Agile/BDD ↔ 本專案）

常有人問「這份規格為什麼不是 Persona → Epic → User Story → BDD 那一套？」——它其實就是，
只是走 **ISO/IEC/IEEE 29148（SRS）＋ use-case scenario ＋ V-model 追溯** 學派，而非
**Agile/BDD（Cohn/North）** 學派。兩者都是正統，對合約級、重跨角色旅程的 B2B2C 派工平台，
前者更合身。對照表：

| Agile/BDD 正統 | 本專案節點／正典 | 說明 |
|:---|:---|:---|
| **Persona** | `PER-*`（`06_UX_Research_Report.md §3`）| 誰。追溯鏈「誰」那一端（CR-0185）|
| **Epic / Theme** | 五分線 `L1-CUS/OPS/TEC/KNW/PLT`（`28_Scenarios §1`）| 價值鏈主軸，當標籤用，不另鑄 ID |
| **User Story** | `SC-*`（`28_Scenarios`）| 旅程粒度的 use-case，非 atomic story（刻意）|
| **Acceptance Criteria** | `SC.完成判定` ＋ `FR.後置與驗收`（`04_SRS`）| 做到什麼算完成 |
| **BDD Scenario（Gherkin）** | `bdd/*.feature` ＋ `28_Scenarios` 內嵌生成塊（`_render_bdd.py`）| **SC 的生成視圖**，非第五套編號 |
| **Test Case** | `TC-*`（`20_Test_Cases`）| 實際輸入、步驟、預期 |

完整追溯鏈：**`PER → SC → {FR/NFR} → TC`**，BDD 是其上的可讀投影。要點：
`User Story` 不砍成 atomic（跨角色旅程會被打碎）、`NFR` 不逼進「作為…我想要…」句型
（它是全域地板，見 §4）、`BDD` 一律生成不手維護（否則變 §1 講的「同一旅程寫多次」）。

### 與 Plane 的階層詞彙對照（2026-08-05 對標守則 v1.3）

四書投影進 Plane 時要落在《Plane QA 工程守則 v1.3》Part B 定義的階層上。
**這不是第三套編號，是同一批節點在另一個系統裡的層級名稱**：

| 守則型別 | level | `needs_acceptance` | 四書的哪一段 | 數量 |
|:---|:---:|:---:|:---|---:|
| `Epic` | 0 | ✅ | **五條價值線 `E-CUS/OPS/TEC/KNW/PLT` ＋ 地板 `E-GLB`** | 6 |
| `Feature` | 1 | ✅ | **`28_Scenarios` 的 SC-01–19 旅程**（19）＋ 地板屬性群（`地板-功能` ＋ 17 個 NFR category） | 37 |
| `Story` | 2 | ✅ | `04_SRS` 的 FR（65）＋ `05_NFR` 的 NFR（106） | 171 |
| `Task` | 3 | ❌ | `27_Product_Roadmap_WBS` 的工作包（源檔 49，扣掉 `wbs_disposition` 標 archive 的 21）| 28 |
| `Bug` | 2 | ❌ | 缺陷，執行期由 failed／blocked 結果原子建立 | 0 |

**只有這五個型別，不准再開第六個。** 需求性質（功能／品質）由 `Issue.requirement_kind`
（`functional` / `quality` / `none`）承載——守則 B1／B2：讓 type 兼管性質會使
`type 數量 = 層數 × 性質數`，一個 workspace 因此長到九個 type。

要點四條：

- **① 契約掛 Story 層**（驗收在那裡決定）。Epic 與 Feature 的每個數字都沿 `Issue.parent`
  roll-up，沒有獨立來源——roll-up 一旦算錯，不是某一格錯，是中上層全部是假的。
- **② NFR 與 Story 同階，不另開子層**（也不再有 `Quality requirement` 型別）。NFR 橫跨所有
  層級，做成子層會逼它選一個歸屬；性質改由 `requirement_kind=quality` 標。
- **③ WBS 是 Task 不是 Story** —— 它有負責人、有前置依賴、用技術語彙，是 PMBOK 的交付物分解，
  不是價值切片。且 **Task / Bug 的 `needs_acceptance` 必須顯式關掉**：平台預設 `true`，
  不關會讓 49 張工作包整批被要求驗收契約、集體顯示為未覆蓋。
- **④ 子系統（agent / api / web…）不是 Epic，是 Module。** 它是技術切法；一個 sprint 交付的
  價值橫跨多個子系統，拿它當 Epic 會讓 roll-up 讀不出「哪幾條客戶旅程跑得通」——而那正是
  管理層唯一會問的問題。

#### 旅程進了拆解樹（2026-08-05 形狀變更）

原本 SC 刻意留在 parent 樹之外（理由：一張卡只有一個 parent，而旅程橫跨多個子系統）。
**Epic 換成價值線之後這個理由消失了**——旅程本來就屬於某一條價值線，五分線與 SC 是
一對多、不是多對多。於是 SC 升格為 `Feature`，覆蓋率沿 `Story → SC → 價值線` roll-up。

代價落在下一層：`SC × FR` 仍是 M:N（一條 FR 服務多條旅程），而 `Issue.parent` 是單值。
處理方式是 `sc_requires_rq.yaml` 新增可選欄 **`primary: true`**，宣告這條 FR 在拆解樹上
選哪條旅程當 parent。三條規矩：

1. **`primary` 不是新的追溯邊。** 追溯仍是 M:N 的 `sc_requires_rq`，它只解決載體限制。
2. **判不出來就留空，不猜。** 唯一 `essential` 邊可自動推；多條 essential 或只有 supporting 的，
   一律等人工宣告。未宣告者在 Plane 上 parent 為空、落進 None 組——階層跳級刻意不掩蓋。
3. **NFR 一律不吃這條規則**，全部掛 `E-GLB` 底下依屬性分的地板 Feature。把有 SC 邊的那
   20 條掛進旅程，會讓旅程覆蓋率被品質地板稀釋。

#### 🛑 兩個字在兩張表裡不是同一件事

上面兩張表都有 `Epic` 與 `Story`。**改用價值線當 Epic 之後，`Epic` 這個字已經對齊了**
（兩張表都指五分線）；剩下 `Story` 仍然不同，講的時候要指名：

| 詞 | 在「Agile/BDD 學派對照」表（上一張）| 在「Plane 守則階層」表（這一張）|
|:---|:---|:---|
| **Epic** | 五分線 `L1-CUS/OPS/TEC/KNW/PLT` | **同左**（2026-08-05 起一致） |
| **Story** | `SC-*` 旅程（User Story 的近親）| `FR-*` / `NFR-*` 需求；旅程在這裡是 `Feature` |

**裁決：xlsx 與 Plane 一律採右欄（守則）定義**——四書是為這套流程服務的，投影進系統的東西
就得用系統的名字。左欄只在「向敏捷背景的人解釋這套規格屬於哪個學派」時使用，且必須明講是類比。

實務上記三條就不會錯：**① 五分線在 Plane 是 Epic**（2026-08-05 前寫的是 Module，已作廢）；
**② 旅程 SC 在 Plane 是 `Feature`，在拆解樹上**（2026-08-05 前寫的是「Scenario 型別、不進樹」，
已作廢）；**③ 講「Story」時預設指 FR / NFR**，要指旅程就說「旅程」或「SC」。

#### Sprint 迭代靠 Cycle，那是排程軸不是階層

守則 B0 的四個正交軸裡，**排程軸（Cycle / Module / Milestone）是切面，不是階層**：
一條 Story 可以同時在 Sprint 03、屬於「子系統 API」模組、掛在 M2 里程碑下，誰也不包含誰。

2026-08-05 前 `_plane/` 全庫 `cycle` 出現 **0 次**——沒有 sprint 容器，迭代無從談起。
現由 `import_spine.py` 建立 `Sprint 01`–`Sprint 06`（各 2 週，冪等）。
**但不自動把 Story 塞進 cycle**：排程是 PM 的決策（守則六個 human gate 之一），
agent 只建容器。

#### 卡片標題怎麼寫（2026-08-05 補：原本只裁決詞彙，沒裁決格式）

上面裁決的是「哪一層叫什麼」，不是「一張卡的標題長什麼樣」。標題格式一直只活在生成器
程式碼裡、沒被寫成規則——結果 Task 層漏了前綴、地板 Feature 標題自我重複。補上。

**通則：`<正典編號> <正典名稱>`，一個半形空格分隔。**

| Plane 型別 | 標題長相 | 編號來源 | 生成處 |
|:---|:---|:---|:---|
| `Epic` | `E-CUS 終端客戶價值線` | `_spec_data.VALUE_LINES` / `GLOBAL_EPIC` | `rebuild_hierarchy.py:224` |
| `Feature`（旅程）| `SC-01 產品疑問自助解決（不建卡）` | `28_Scenarios` | `import_spine.py:447` |
| `Feature`（地板）| `地板-Sec 安全性地板` | 代號在 `rebuild_hierarchy`，名稱在 `_spec_data.FLOOR_NAMES` | `rebuild_hierarchy.py:261` |
| `Story`（FR）| `FR-AGT-01 LINE 進線與驗簽` | `04_SRS` | `import_spine.py:473` |
| `Story`（NFR）| `NFR-<Cat>-NN <目標名>` | `05_NFR` | `import_spine.py:494` |
| `Task`（WBS）| `WBS-1.2 <工作包名>` | `27_Product_Roadmap_WBS` | `import_spine.py:651` |
| `Bug` | `<TC-ID> <一句話症狀>` | 失敗／阻塞的 TC | 尚未實作 |

**空格前鎖死，空格後隨便潤。** 這不是風格偏好，是 `by_code()`
（`rebuild_hierarchy.py:96-118`）的索引契約：它優先讀 `canonical_id` 自訂欄位，讀不到
才退回「標題第一個 token」。所以：

- **動了前綴**——有 `canonical_id` 的卡還認得出來，靠退回路徑的那批會判成「不存在」，
  下次重跑再開一張同代號的卡。
- **動了空格後的敘事**——完全安全。要把 Story 改寫成「作為…我想要…」句型技術上做得到，
  前綴留著即可。§0 那句「NFR 不逼進句型」講的是**不強制**，不是不准。

三條禁令：

1. **不准拿掉編號換成純敘事**——那是把追溯錨點交到人類潤稿的手上。
2. **不准把狀態／負責人／日期／進度塞進標題**（`[進行中]`、`@Alice`、`W32`）。那些都有
   欄位；塞進標題會讓 `by_code()` 的退回路徑切出垃圾 token。
3. **不准 xlsx 與 Plane 用兩套名稱。** 地板名稱因此只有一份：`_spec_data.FLOOR_NAMES`
   ＋ `floor_name()`，`_build_workbooks` 與 `rebuild_hierarchy` 都問它。05_NFR 新增
   category 時 `floor_name()` 直接炸，逼人命名——回一個 `f"{cat} 品質地板"` 預設值，
   等於讓新屬性以一個沒人讀得懂的名字混進看板，而且兩邊各補一次就又分岔了。

##### 三項落地（2026-08-05，本節連同守則一起生效）

- **T1｜Task 標題補 `WBS-` 前綴**（`import_spine.py:651`）。原本送 `f"{wid} {name}"`，
  看板上是「1.2 xxx」，`by_code()` 退回路徑切出的 `1.2` 與其他四層不同構。
  `canonical_id` 同步帶前綴，維持「標題前綴 == canonical_id」的不變式（`_plane/README §7`）。
  三個連動點：`WBS_TITLE` 正則把前綴設為**可選**（遠端人工卡是裸號 `1.1.1 …`，兩種都要
  認得，否則 id_map 遺失後的認領路徑會漏掉一批）；認領時補寫人工卡的 `canonical_id`
  （**標題不動**——別人的卡只接管型別與歸屬）；`rebuild_hierarchy` 的 Task 反查改用
  `WBS-{wid}`，兩批卡因此共用同一條路徑，不必在呼叫端寫 fallback。
- **T2｜地板 Feature 改用中文全稱**（`_spec_data.FLOOR_NAMES`）。原本 17 個 category

  （Plane 側原本叫「全域功能地板」）。
- **T3｜§0 對照表的 Task 數量 49 → 28**。49 是 `27_Product_Roadmap_WBS` 的源檔工作包數，
  archive 的 21 個由 `import_spine.py:628-630` 濾掉不進 Plane。同欄其他列都是 Plane 端
  數量，只有這格不是（`_plane/README §2.1` 早就寫 28，是本文件沒跟上）。

## 1. 脊椎是情境，不是功能

2026-07-27 重構前，同一段客戶旅程被寫了四次、四套編號、四種粒度：

| 來源 | ID | 數量 | 視角 |
|:---|:---|---:|:---|
| `07_Journey_Map.md` | 旅程 A–E | 5 | 角色旅程 |
| `08_User_Flow.md` | UF-01–UF-10 | 10 + 12 例外 | 系統流程 |
| `19_Test_Plan.md` | TS-01–TS-12 | 12 | 測試情境 |
| `22_UAT_Report.md` | S1–S5（今 UAT-01–UAT-05）| 5 | 驗收腳本 |

四套沒有一套能當主鍵：A–E 太粗、UF 是系統視角（客戶不會說「我要走 UF-06 狀態機」）、
TS 是 QA 事後歸納、S1–S5（今 UAT-*）是 UAT 腳本。65 條 FR + 106 條 NFR 全掛在一個**不存在的主鍵**上，
所以拿到 Excel 的人找不到脊椎在哪——那不是資訊太多，是沒有入口。

現在唯一脊椎是 **`28_Scenarios.md` 的 SC-01–SC-19**，上述四套全部降級成對 SC 的投影或別名。

```text
   誰            訪談              SA 翻譯          架構落點          QA 證明
   ──────────────────────────────────────────────────────────────────────────
   PER-*  ────►  SC-*  ──────►   FR / NFR  ──────►  Component  ──────►  TC
                  │                  │                                   │
                  └──────────────────┴───────────────────────────────────┘
            驗收控制表         BOM              整合測試計畫

                規劃書 ＝ 上面三者的差集（經營層）
```

一條 Scenario 通常長出 5–15 條 Requirement；一條 Requirement 通常服務多條 Scenario
（「技師必須通過 KYC 才能接單」同時撐住註冊、接單、結算三條旅程）。兩邊都是一對多，
所以 `SC × RQ` 是 M:N —— 這也正是「一條 FR 配一段 VOC」必然複述的原因。

## 2. 四書定位：一本一個角色、一個問題、一個狀態軸

| 書 | 交給誰 | 只回答一個問題 | 列節點 | 狀態軸誰推 | 分頁 |
|:---|:---|:---|:---|:---|---:|
| `SmartLock_業務邏輯驗收控制表.xlsx` | 業務 Owner / PM | 客戶的哪幾條旅程算不算驗收通過？ | SC | 只有人 | 5 |
| `SmartLock_模組功能BOM.xlsx` | 架構師 / RD | 每條需求由誰實作、現在到哪了？ | FR / NFR | 掃描器 | 3 |
| `SmartLock_整合測試計畫.xlsx` | QA | 我今天要跑哪些案例、怎麼判定通過？ | TC | 測試執行 | 5 |
| `SmartLock_規格統控規劃書.xlsx` | 經營層 / PM | 哪裡有洞、哪裡卡決策、什麼時候做？ | 缺口（差集） | findings | 3 |

每本固定三段結構：**① 怎麼用這本**（含 RACI）→ **② 主表**（唯一一張，可 filter，人要填的欄留白標黃）
→ **③／④ 展開與回查**（連到正典，不複製內容）。驗收控制表另有 **④ 旅程 × Persona**（誰在走）與
**⑤ BDD 行為情境**（由 SC 卡＋Persona 生成）兩張生成分頁，把「誰」與「可驗證行為」補進 SC 書（CR-0185）；
整合測試計畫另有 **⑤ UAT 走查腳本**（由 `22_UAT_Report §4` 生成，見下）。

### 四個角色各站哪一層

| 角色 | 主要操作的層 | 這層的驗收問題 |
|:---|:---|:---|
| 業務 / PM（訪談期） | Scenario | 客戶的旅程走得完嗎？ |
| SA | Scenario → Requirement 的翻譯 | 每條 FR 都能反指到某段旅程嗎？ |
| 架構師 | Requirement → Component | 每條 FR 都有元件負責嗎？ |
| QA | 兩層都要 | Scenario 測「順不順」、Requirement 測「對不對」 |

SA 那一格是關鍵：**一條 FR 若無法反向解釋「它為了哪段旅程存在」，那條 FR 就是想像出來的。**
BOM ② 的「服務旅程」欄就是這條檢查，標 `⚠ 無旅程` 的列要嘛補 SC 邊、要嘛宣告 global、要嘛刪。

### 為對標 Plane 新增的欄位（2026-07-28）

九個欄位，全部由 `_build_workbooks.py` / `_canon.py` 生成，**不手改 xlsx**：

| 分頁 | 欄位 | 內容與由來 |
|:---|:---|:---|
| BOM ② | `parent 代號` | 203/211 列有值（8 個空的是 L1 本身）。原本的樹只靠**列序隱含**，匯入器推不出父子關係，Plane 的 roll-up 就沒有路徑 |
| BOM ② | `requirement_kind` | `functional` 65（FR）／`quality` 106（NFR）／`none`（Task・Bug）。**2026-08-05 正名**：原欄名 `需求型別`、值為 `Story` / `Quality requirement`——守則 v1.3 已廢除 `Quality requirement` 這個 work item type（type 兼管性質會讓數量變成 `層數 × 性質數`），性質改由 `Issue.requirement_kind` 承載 |
| BOM ② | `目標里程碑` ＋ `節點範圍` | 取代舊的 M1/M2/M3+ 三欄。`Issue.milestone` 是**單值 FK**，容不下 `M1→M3` 這種區間，故目標里程碑取區間終點（M1 43／M2 14／M3 6／M4 2），完整區間另存節點範圍欄，5 條跨節點 FR 的資訊不丟 |
| BOM ② | `NFR 驗證形態` ＋ `ReleaseEvidence key` | 由 `05_NFR` 既有的 `verification` 欄推導，不用前綴猜。單一形態 1 門檻量測 45／2 掃描 7／3 審查 31／4 持續 SLO 19，另 4 條跨形態標 `⚠`。形態 3/4 共 50 條走 release gate 外部證據 → 產生 ReleaseEvidence key（54 個，含跨形態） |
| 驗收表 ⑤ | `涵蓋需求（由 SC 邊推導）` | 64 條 BDD 全有值。**粗對應**——沿 SC 邊展開，不是 BDD 逐條對需求的精確映射 |
| 測試計畫 ② | `路徑類型` ＋ `驗證面向` | 舊的「類型」欄把兩個維度混在一格（`權限+例外`、`failure+recovery`）。守則 B2 明文禁止用同一欄表達兩件事，故拆成正交兩軸 |

兩個刻意的設計，改之前先看懂：

- **`NFR 驗證形態` 回傳所有命中形態，不是第一個。** 驗證方式寫「secret scan + audit」的需求真的橫跨
  掃描與審查，守則 B3 要求拆成兩條需求分開寫；靜默挑一個會讓另一半永遠驗不了，而閘門看不出來少了什麼。
- **`路徑類型` 空著就是空著（52/130）。** 不填預設值——填 `happy` 會讓「這條需求只測了正常路徑」
  這個真缺口消失，而那正是這欄存在的理由。

### UAT 走查腳本進 Excel：新增《整合測試計畫》⑤（2026-07-29）

先前 UAT 這一層只活在 `22_UAT_Report.md`，Excel 只看得到 `UAT-01`–`UAT-09` 這個**編號**，看不到要走什麼。
新增 **⑤ UAT 走查腳本（UAT-01–UAT-09）** 分頁，由 `_canon.load_uat_scripts()` 解析該檔 §4 生成：
腳本名稱、涵蓋旅程、旅程數、案例數、逐項步驟、驗收點，加上四個給 QA 填的黃欄
（走查結果 / 執行日 / 主持人 / 異常紀錄）。

**④ 與 ⑤ 差在哪 —— 這是最常被搞混的一組：**

| | ④ 旅程驗收腳本 | ⑤ UAT 走查腳本 |
|:---|:---|:---|
| 一列是什麼 | 一條旅程（`SC-NN`） | 一場走查（`UAT-NN`） |
| 數量 | 19 | 9（＋1 列「不走走查」） |
| 它是**什麼的單位** | **簽核**：這條旅程算不算過 | **執行**：UAT 當天照著走 |
| 在 Plane | 一列＝一條 **TestRun** | **沒有對應物件**，只寫進 run 名稱當註記 |

兩者是多對一（UAT-01 涵蓋 SC-01/02/03，UAT-02 涵蓋 SC-04–07），**誰也取代不了誰**：
只有 ⑤ 答不出「自助解決那段到底過了沒」；只有 ④ 則沒人知道當天要照什麼順序走。

⑤ 的最後一列是 `uat: null` 的兩條旅程（SC-09 月結對帳、SC-13 跨品牌對帳）。它們有自己的案例
與 TestRun，只是**不掛在任何走查腳本下**——月結 cron、七帳本對帳沒有人能「走一遍」給你看，
硬編一支走查腳本只是造假。列出來是為了讓「19 條旅程」與「9 場走查」的差額不會憑空消失。

解析採**依標題取值**（`### UAT-NN <名稱>`、`1.` 步驟、`- **驗收點**：`），不用位置索引——
§4 是手寫散文、每支腳本步驟數不同，位置取值會在有人加一步時靜默錯位（這個教訓來自 WBS，
見 commit `7202f705`）。

## 4. 四條邊，各自宣告，互不推導

真相源在 `_relations/`，一列一條邊，每條都必須說得出「憑什麼成立」：

| 檔 | 邊 | 誰寫 | 這條邊回答 |
|:---|:---|:---|:---|
| `sc_embodies_persona.yaml` | `SC ──► PER` | BA | 這條旅程由誰感知（primary/secondary）|
| `sc_requires_rq.yaml` | `SC ──► RQ` | BA / SA | 這條旅程需要哪些需求 |
| `rq_verified_by_tc.yaml` | `RQ ──► TC` | QA | 這條需求由哪些案例驗證 |
| `sc_verified_by_tc.yaml` | `SC ──► TC` | 驗收設計 | 這條旅程的驗收腳本跑哪些案例 |

`sc_embodies_persona.yaml` 是追溯鏈「誰」那一端（CR-0185），與其餘三條同樣**宣告非推導**：
不由 SC 的 Actor 字串命名相似度腦補（V2 精神）。BDD 生成視圖的 `As a <persona>` 取自它的
primary 邊，再接 06_UX §3 的 Persona 成功定義。

**第三條絕對不可以由前兩條算出來。** 前兩條合成可推出「這條需求實際會被哪些旅程驗到」，
與第三條宣告的差，就是 **V9 驗收覆蓋缺口**——若第三條是算出來的，V9 恆等於零，等於沒有檢查。

`_relations/` 底下還有第五個檔 **`wbs_disposition.yaml`，它不是邊**，是 49 張 WBS 工作包在
Plane 守則模型下的**處置對照**（archive / merge / enabler / rebuild 四類）。它之所以放這裡，
是因為它跟四條邊一樣是「人宣告、不可推導」的判斷；但它不進 `_validate_relations.py` 的邊檢查，
也不影響四書生成 —— 它只在把卡片推進 Plane 時被讀。**不要把它當第五條邊寫進追溯鏈。**

`sc_requires_rq.yaml` 另有 `global:` 區塊，宣告「拿掉任何一條旅程它依然必須成立」的需求。
NFR 天生不掛單一 Scenario：「可用性 99.9%」不對應任何一段客戶旅程，它是所有旅程共用的地板。
為 106 條 NFR 各硬掰一段 VOC 寫出來一定假——那不是文案問題，是模型放錯位置。

`sc_requires_rq.yaml` 另有可選欄 **`primary: true`**（2026-08-05 隨旅程升格 Feature 加入，
只允許出現在 `role: essential` 的邊上）。**它不是第五條邊**，也不改 M:N 的追溯語意——
它只回答一個載體問題：`Issue.parent` 是單值，而一條 FR 服務多條旅程時，Plane 的拆解樹
要選哪一條當 parent。判不出來就留空、不猜（V14 會把它列成 finding）。

65 條 FR 的去向（2026-08-05 實測）：

| 情況 | 條數 | 誰決定 |
|:---|---:|:---|
| 只有一條 `role: essential` 邊 | 27 | 機器自動推 |
| 已宣告 `§global`，掛地板 Feature | 6 | 已定案 |
| **判不出來 → 待裁決** | **32** | **BA** |

待裁決清單見 [`_relations/PENDING_PRIMARY.md`](./_relations/PENDING_PRIMARY.md)（21 條有多條
essential 挑一條即可；11 條只有 supporting，要先把某條邊升為 essential 才能標——V12 擋
supporting 上的 primary）。**空白修得掉，猜錯修不掉**：猜錯的 parent 在畫面上與正確答案
長得一模一樣，只是該旅程的覆蓋率從此多算一條、真正該扛它的旅程少算一條。

## 5. 機器檢查（`_validate_relations.py`）

| 規則 | 檢查什麼 | 等級 |
|:---|:---|:---|
| V2 | 邊的端點都存在於正典（不許用命名慣例偽裝關聯） | error / finding |
| V3 | 同一對 (src, dst) 不重複 | error |
| V4 | `role` / `kind` 在值域內 | error |
| V6 | 真相源不得出現推導欄（`scenarios` / `covered_by` / `uat`） | error |
| V7 | 只有測試設計、還沒有具體案例 | finding |
| V8 | 孤兒節點：旅程沒需求、需求沒旅程且未宣告 global | finding |
| V9 | 宣告需要某需求，驗收腳本卻沒跑到任何驗證它的案例 | finding |
| V10 | P0 旅程的需求只有 happy、缺 failure/recovery | finding |
| V11 | 旅程沒有主要 Persona，或 Persona 未被任何旅程體現（裝飾性節點）| finding |
| V12 | `primary: true` 只出現在 `role: essential` 的邊上 | error |
| V13 | 同一條需求最多一條 `primary: true` | error |
| V14 | FR 既無唯一 essential、又無 `primary`、又不在 `global:` → 在 Plane 上會沒有 parent | finding |

**error 擋生成，finding 不擋。** 擋生成只會逼人用假資料把洞填平，那比洞本身更糟。
所有 finding 一律進《規格統控規劃書》② 缺口與決策清單，每列都帶責任角色與人工決策欄。

V10 存在的理由：訪談若只問「誰、什麼時候來、要達成什麼、卡在哪」四題而不問
**「什麼情況算失敗」**，產出的規格全是 happy path，代價在 UAT 前兩週結清。

```bash
python3 _build_workbooks.py             # 再生四份 xlsx + 字典 + 健康報告
```

  等於把同一段旅程摘要 171 次；方法與判準的真相源是各節 TC 的「步驟／預期」與 `05_NFR` 目標值欄。
- `_extract_rq_tc.py` — **已用畢，不可重跑**。2026-07-27 一次性把 §2.1 舊版「指定 TC」欄攤平成
  `rq_verified_by_tc.yaml`，保留作為該表的來歷紀錄。
- `_plane/` — 四書 → Plane 專案管理系統的轉換層（見 `_plane/README.md`）。它是這張單向圖的
  **另一個葉節點**，與 xlsx 平行、不互為前置：


## 8. 狀態軸不得互推

| 軸 | 誰推進 | 來源 |
|:---|:---|:---|
| 需求定版 | SA | `04_SRS` / `05_NFR` 文字訊號（🔜 / [待確認]） |
| 工程證據 | RD / 架構師 | `_spec_data.py` codebase 掃描（AS-BUILT / PARTIAL / TO-BE） |
| 測試執行 | QA | 測試執行結果 |
| 驗收通過 | 業務 Owner | **只有人能推進** |

Plane 的覆蓋率 roll-up **不是第五個軸**：它把契約狀態沿 `Issue.parent` 往上彙總，
彙總的來源仍然是軸③（測試執行）。同理，出貨閘門的 `ready: true` 只代表「機讀檢查沒有攔截項」，
**不代表軸④（驗收通過）已推進** —— 那永遠只有人能推。

程式檔存在 ≠ 工程完成；工程完成 ≠ 測試通過；測試通過 ≠ 驗收通過。
舊版健康報告的 `AS-BUILT 14 / PARTIAL 17 / TO-BE 1` 是**模組完成度**，不是旅程完成度——
它回答不了業務跟客戶開會時唯一被問的問題：「哪幾條客戶旅程現在跑得通」。

完整數字與每次重生結果見 [產出健康報告](./產出健康報告.md)。
