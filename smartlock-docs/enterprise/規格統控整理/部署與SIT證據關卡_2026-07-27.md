# 部署與 SIT 證據關卡（2026-07-27）

> **結論先行**：程式已具備 `DB_URI_STRICT`、跨 portal token guard、Redis／Kafka／OTLP
> 的可選執行路徑；但此工作區沒有 `gcloud` CLI 或可驗證的 Cloud Run／SIT 存取權，故**沒有
> production/SIT 實測證據**。本文件把「可從程式推得」與「必須從環境取證」拆開；未附證據一律
> 視為未通過，不能因程式存在而標記為已上線。

## 1. 證據判讀規則

| 證據等級 | 可回答的問題 | 不可宣稱 |
|---|---|---|
| AS-BUILT | 程式是否有路徑、守衛與測試 | Cloud Run revision 是否帶正確 env／secret，依賴是否連得上 |
| SIT | 對 prod-mirror 是否實際可達、能否處理故障與復原 | 生產流量、真 LINE 或生產資料已驗收 |
| PROD | 實際 revision、設定、監控與 smoke 結果 | 長期可靠性（仍須觀察窗與 incident drill） |

**每份證據的最低欄位**：環境、服務/revision、UTC 時間、操作者、git SHA、執行命令（不得含
secret）、原始輸出位置、結論（pass/fail/blocked）。截圖可輔助，但不能代替命令輸出或 trace ID。

## 3. 必跑關卡（依序；任一 fail 即停）

### G0：部署設定取證（Release Manager）

在有權限的受控 runner 執行，將**去敏後**輸出放入 release evidence 儲存區。不得輸出 secret 值。

```bash
gcloud run services describe smart-lock-api --region asia-east1 --format export
gcloud run services describe lock-tech-api --region asia-east1 --format export
gcloud run services describe lock-platform-api --region asia-east1 --format export
```

驗收：

- 各 revision 的 `DB_URI_STRICT=1`；brand / tech / platform 的 `ALLOWED_TOKEN_PORTALS` 分別只能含
  `brand` / `tech` / `platform`（除非有已核准的例外 ADR）。
- tech service 有 `TECH_POSTGRES_URI`；platform service 有 `TECH_POSTGRES_URI` 與
  `PLATFORM_POSTGRES_URI`；品牌面不得把 platform 資料庫混作 tenant 資料庫。
- 若 `maxScale > 1`，必須有 `REDIS_URL` 的**secret reference**及 G3 證據；否則縮回單實例。
- 如宣稱 Kafka 或 SigNoz 已上線，revision 必須帶 `KAFKA_BOOTSTRAP`／
  `OTEL_EXPORTER_OTLP_ENDPOINT`（值以遮罩或 secret reference 呈現即可）。未帶即標示「功能 no-op」。

### G1：三庫 migration 與 drift（DBA）

先建立可回復備份，對三個 prod-mirror URI 執行以下命令；URI 僅由 secret 注入 runner，不寫入
shell history 或證據檔。

```bash
scripts/db/apply-schema-routed.sh --dry-run
python3 scripts/ci/migration-drift-check.py --check-db
```

驗收：三庫 target migration 全數匹配 `public.schema_migrations`；不得有未套用或 ghost migration。
記錄每庫 migration 數、SHA 與輸出 hash。`--dry-run` 成功不等於已套用，正式套用須另有 DBA 變更單。

### G2：API 契約、strict mode 與跨面拒絕（QA/SRE）

```bash
uv run python scripts/ops/export_openapi.py --output /tmp/openapi-runtime.json --pretty
SMOKE_BASE_URL="$SIT_API_URL" SMOKE_AUTH_TOKEN="$SIT_ADMIN_TOKEN" \
SMOKE_TENANT_ID="$SIT_TENANT_ID" python3 scripts/ops/smoke_test_production.py --output-json sit-smoke.json
```

驗收：

- runtime spec 有 `POST /tenants/{tenantId}/work-orders/{id}/consents:send-link`，operationId 為
  `sendWorkOrderConsentLinkV2`；靜態 `api/openapi.yaml`／`16_API_Spec.yaml` 同步。
- `TC-PLT-SURFACE-01`：錯 portal token 403，且 audit 證明拒絕前未讀取目標資料。
- `TC-NFR-SCH-01`：缺 DB URI 的啟動嘗試 fail-closed；完整 URI 時 health ready。
- `TC-DISPATCH-09` 與 `TC-PAYMENT-01` 的失敗／恢復證據保存 request ID、trace ID 與資料庫 audit。

### G3：Redis、Kafka、SigNoz、Refinery 的故障與復原（SRE + QA）

| 元件 | 最小 SIT 演練 | 通過條件 |
|---|---|---|
| Redis | 兩個 API instance 各開一 WS；跨 instance fanout；暫停 Redis 後再恢復 | 正常時兩端收到一次；故障有 `WS_BRIDGE_ALERT`；恢復後不重複或靜默遺失 |
| Kafka/Redpanda | 發工單事件、暫停 consumer、恢復、重送同一事件 | outbox/consumer 可對帳；lag 可觀測；projection/settlement 不重複 |
| SigNoz | API→agent→refinery 測試流程；注入 PII 與 5xx | 同一 trace 可串接；span 無明文 PII；error/latency alert 可定位 revision |
| Refinery | 指定 tenant 的 bronze intake→draft→HITL approval→雙路 publish；再送跨租戶／未授權來源 | `REFINERY_TENANT_ID` 未設或越權皆拒絕；未核可零落地；provenance/audit 可回查 |
