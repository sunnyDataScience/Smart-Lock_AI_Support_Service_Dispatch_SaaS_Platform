# 待裁決：FR 在拆解樹上的 parent（`primary`）

> **這不是真相源，是一張勾選用的工作單。** 裁決寫回 `sc_requires_rq.yaml` 對應那條邊（加 `primary: true`）之後，本檔即可丟。
> 內容由 `_validate_relations.py` 的 V14 finding 產生（2026-08-05 的 yaml 狀態）；yaml 改過就以重跑 `python3 _validate_relations.py` 的結果為準，不要以本檔為準。

## 為什麼需要人來勾

`sc_requires_rq.yaml` 是 M:N 的追溯網——一條需求本來就可以同時服務多條旅程，這不是資料髒，是事實。但拆解樹上的 parent 只能有一個。

落差就這樣而已，所以 `primary` **只回答一個問題**：這條需求在樹上掛誰底下。標了它，其他 SC 邊一條都不會變弱，追溯照舊。

為什麼不讓程式挑：挑錯的 parent 在畫面上跟正確答案長得一模一樣——需求好端端掛在某條旅程下，沒有任何警示，而該條旅程的覆蓋率從此多算一條、真正該扛它的旅程少算一條。留空則會在 V14 與樹上的「無 parent」組裡自己現形。**空白修得掉，猜錯修不掉。**

## 65 條 FR 的去向

| 情況 | 條數 | 誰決定 |
|:---|---:|:---|
| 只有一條 `role: essential` 邊 | 27 | 機器自動推，不需要人 |
| 已宣告 `§global`（掛地板 Feature） | 6 | 已定案 |
| **判不出來 → 本清單** | **32** | **BA** |
| 合計 | 65 | |

補一句避免對帳對不上：完全沒有 SC 邊的 FR 有 5 條（FR-DAT-02、FR-DAT-05、FR-PLT-06、FR-WEB-02、FR-WEB-07），它們**已經**全部列在 `§global`，走地板 Feature、有 parent，所以不在本清單裡，不需要裁決。

## 怎麼勾

1. 每個 FR 區塊挑**一列**打勾（把 `☐` 改成 `☑`）。挑「拿掉這條旅程，這條需求就失去主要存在理由」的那一條。
2. 勾 `essential` 那列 → 直接在 yaml 該邊加 `primary: true`，收工。
3. 勾 `supporting` 那列 → **要先把那條邊升為 `essential`**（V12 擋 supporting 上的 primary），並改寫該邊的 `note` 說清楚它憑什麼變成關鍵路徑，再標 `primary: true`。
4. 勾「都不是」那列 → 這條 FR 其實是所有旅程共用的地板，移進檔尾 `§global`（判準：拿掉任何一條旅程，它依然必須成立）。
5. 理由若不只是「這條最主要」，補進該邊的 `note`——那一欄是人工判斷留在專案裡的唯一痕跡。

每列都附了該邊的 `note` 原文與旅程優先級，就是為了讓這件事不必回頭翻 yaml。
