## 2. 目標架構原則

1. **品牌 DB 是第一租戶邊界，`tenant_id` 是防禦與稽核邊界。** 不新增 Plane 式
   workspace/project 階層；技師資料留 `lock_tech`、平台治理留 platform DB。
2. **前端可樂觀，後端必權威。** 每個 mutation 都要有 idempotency、授權、version/conflict
   語意與可恢復 UI；前端隱藏按鈕從不是安全控制。
3. **同步資料有唯一 owner。** UI preference、業務狀態、技師資料與平台治理各存其
   權威庫，禁止為「方便同步」建立第四份通用 user DB。
4. **慢工作以 durable record 驅動。** request 只寫交易與 outbox；worker 可重試、可觀測、
   可重播，且不因 API scale 而失控。
5. **人與機器是不同 principal。** 真人走 OIDC / session；服務走 short-lived 或可撤銷
   credential，最小 scope、可稽核、不可共用真人帳號。
6. **發布是受證據約束的產品流程。** 通過 CI 不等於可上 production；migration、secret、
   health、SIT、rollback 與可觀測性要形成同一 release evidence。

## 3. 建議導入項目

### A. 統一前端 mutation 與同步策略（P0）

**要解的問題**：現行 `cacheInvalidate("GET:")` 能避免 stale，但所有 mutation 都清整個
GET cache，沒有共用的 optimistic rollback、錯誤分類與版本衝突體驗；跨 portal 重複維護。

**設計**：

- 建立每個 portal 可共用的 `mutation contract`：`optimisticPatch`、`rollback`、
  `invalidateKeys`、`idempotencyKey`、`conflictHandler`、`toast/audit outcome`。
- 只對低風險、可逆且 UI 可明確還原的操作採 optimistic：acknowledge、assign UI state、
  收藏、偏好、已讀通知。
- 報價核可、工單狀態、結算、退款、權限與 consent 一律採 **server-confirmed**；可先顯示
  pending，不得假定完成。
- API 對可併發編輯的資源補 `version` / `updated_at` precondition；衝突回 `409` 與
  machine-readable current version，UI 提供 reload / compare / retry，不能 silent overwrite。
- idempotency 的來源統一為使用者 action UUID，而不是重試時每次重生。

**驗收**：離線／5xx／409／重送四類 E2E；不會把未成功的報價、派工或結算顯示為成功；
同一 action retry 不會產生第二筆商業 mutation。

### B. 偏好與導覽模型（P0）

**本機保留**：theme、locale、sidebar 展開狀態、單機的 command history、PWA 安裝提示。
不得放 PII、角色、tenant 或業務真相。

**跨裝置同步**：新增 `user_preferences`（schema 由資料 owner 決定）：

| 使用者 | 權威庫 | 可同步內容 |
|---|---|---|
| 品牌人員 | brand DB | saved view、欄位排序、預設篩選、通知偏好、收藏工單／問題卡 |
| 技師 | technician DB | 工作台排序、服務區偏好、通知偏好、最近操作 |
| 平台管理員 | platform DB | 品牌檢視、治理 dashboard 偏好 |

資料最小模型：`principal_id`、`portal`、`preference_key`、`value_json`、`version`、
`updated_at`；唯一鍵含該庫的 scope。設定 schema allowlist 與大小上限，不提供任意 JSON
垃圾桶。登入 token 不屬偏好；依既有 SSO/cookie 過渡方向移出 localStorage。

### C. Capability-driven Command Palette（P1）

先做品牌後台，不跨四站一次上線。Command 由宣告式 registry 定義：
`command_id`、label、route/action、required capability、context requirement、analytics event。

- UI 只依 `/me/capabilities` 或既有 role policy 顯示可用 command。
- 實際 API 仍經 tenant / role / resource guard；palette 不可繞過 workflow gate。
- 第一批只納入「搜尋工單／問題卡、建立草稿、切換佇列、開通知、跳到已儲存 view」；
  不把 quote approve、settlement、role change 做成未確認快捷命令。
- 最近使用 command 可本機保存；跨裝置的 saved view／favorite 走 B 的資料模型。

**驗收**：鍵盤操作可完成高頻查找與跳轉；同一角色在 URL、palette、直接 API 三條路徑
都得到一致的拒絕結果。

### D. 授權與資源歸屬 contract matrix（P0）

既有 RBAC 是基礎，下一步不是增加角色，而是把 API surface 轉成可檢查矩陣：

| Contract | 必備約束 |
|---|---|
| Tenant resource read/write | path `tenant_id`、JWT/claim tenant scope、resource tenant、active membership 四者一致 |
| Technician resource | tech principal、brand authorization、assignee / allowed projection 一致；不以品牌前端 tenant fallback 代替 |
| Platform resource | platform admin principal；不得接受 `X-Tenant-ID` 取得跨品牌權限 |
| Internal / service call | service principal、audience、scope、request id；不得使用真人 Bearer token |

將每類 router 納入 parameterized BOLA/IDOR contract tests：跨 tenant UUID、已撤銷 membership、
portal claim 不符、過期 service credential、資源不屬於 path tenant。新端點沒有負向案例
不得合併。

### E. Service principal 與 integration credential（P0，受 OD-001／OD-004 約束）

以平台 DB 建立受控 `service_principal` 與 `service_credential`，不是泛濫 API key：

- credential 僅存 hash；明文只在建立當下顯示一次；含 prefix/key id、owner、scope、
  allowed tenant/brand scope、expiry、revoked_at、last_used_at、rate policy。
- 每次使用寫 audit（principal、scope、request id、結果），支援立即撤銷與輪替 overlap。
- 初期用途限定 agent→api、refinery→api、technician OHS；保留 `X-Internal-Token` 僅作
  短暫 migration fallback，並以 metrics 計數歸零後移除。
- OD-001 定案為 OIDC client-credentials 時，credential registry 管 client / secret rotation；
  若保留 internal token，也必須有相同的 scope/rotation/revoke/audit 行為。

**驗收**：沒有一個 production 服務共用人類帳號或永久不可撤銷密鑰；失效／撤銷／錯
audience／跨 tenant 都被 fail-closed 並留 audit。

### F. 從 API lifespan 拆出 background runtime（P0）

盤點確認共有 14 個 cron/outbox worker 與部分 realtime 行為由 API process 啟動。雖已有 PG
advisory lock 與 `min=1/max=1` 防線，仍使 API 的可用性、擴展與排程耦合。

**分兩步，不先引入大規模 Kafka：**

1. **安全化（先做）**：每個 worker 以 job registry 宣告 handler、schedule、idempotency
   key、lock key、timeout、retry、DLQ/人工補償方式與 SLI。保留 outbox/PG lock；補每個
   worker 的 lag、success、retry exhausted、oldest pending metrics。
2. **runtime 拆分**：建立同 repo 的 `worker` entrypoint；由 Cloud Scheduler 以 OIDC 呼叫
   Cloud Run Job（週期類），或以受控 worker service 處理短週期 outbox。API 僅保留 request
   path。每一 job 可安全重跑，寫同一 audit/outbox，不依賴單一 API instance。

Redis 只在跨 instance WS fan-out 與分散式協調完成 SIT 後才允許 API scale-out；Kafka/PubSub
事件骨幹等 OD-002／OD-003 與重播治理完成後再導入。這比先照抄 Plane 的 queue stack 更低風險。

### G. GCP release evidence 與可觀測性（P0）

`cloud-run-deploy` 仍只接受 manual dispatch，現已實作 build-once、staging evidence 與
production environment promotion。目標不是「push 就上 prod」，而是可追溯的 promotion：

```text
PR CI（unit / contract / security）
  → staging deploy（受保護環境，可手動核准）
  → migration / secret / smoke / BOLA / worker SIT evidence
  → production deploy（人工 approval）
  → revision health + trace + rollback window
```

- workflow 加 GitHub Environments：`staging`、`production`；WIF service account 分離，
  production 有 required reviewer。
- 每次 release 寫 deployment manifest：commit/image digest、Cloud Run revision、migration
  versions、config/secret reference（不含值）、health URL、operator、rollback revision、SIT links。
- deployment 路徑依 `api`／`agent`／`web` 變更選服務；不以所有 push 都 deploy `all`。
- 將 G0–G3 做成 required evidence：三庫 strict/portal guard、兩實例 Redis、Kafka replay、
  OTel/SigNoz trace、Refinery tenant negative tests。未通過就不提高 max instances 或宣稱
  production-ready。

### H. Shared contract 優化（P2）

Python 已用 uv workspace；Web 四站現以版本化 `web/shared-contract@0.1.0` 共用 OpenAPI
generated types、RFC7807 decoder、auth/session facade、mutation/conflict 與 capability
types。固定 tarball 由 repo vendor 並寫入四份 lockfile；每站仍保有自己的 UI、route policy、
build 與部署，不導入 Turbo／design system。

## 5. 明確不做

- 不把品牌 DB 重構成 Plane 的 Instance/Workspace/Project 三層；目前物理隔離是產品租戶模型。
- 不在早期導入自由定義 RBAC 或所有功能都做 API token；維持少量固定角色與最小 service scope。
- 不將 token 明文持久化；不讓 service account 與真人帳號共用。
- 不因「有 Cloud Run workflow」就開啟所有 push 自動 production deploy。
- 不在 Redis/Kafka/SigNoz 尚無 deployment/SIT 證據時，把它們當可依賴的 production 基礎設施。
- 不先建立大型共用 UI framework；先共享契約與 mutation/security 行為。

## 6. 量測指標

| 類別 | 指標 |
|---|---|
| 體驗 | mutation 成功後可互動時間、rollback rate、409 conflict rate、command completion time |
| 安全 | BOLA/IDOR negative coverage、403/401 正確率、撤銷 credential 後拒絕延遲、token rotation coverage |
| 非同步 | outbox oldest pending、retry exhausted、job duration/success、duplicate side-effect = 0 |
| 發布 | staging→prod lead time、rollback time、migration/SIT evidence completeness、restore RTO/RPO |
| 多租戶 | 跨 tenant access test = 0 漏失、tenant-scoped query contract coverage |

此規劃應在 OD-001～004 拍板、G0–G3 取證與每個 wave 的 ADR/contract tests 完成後更新；
不以單一 UI demo 或 compose 成功取代 production 架構證據。
