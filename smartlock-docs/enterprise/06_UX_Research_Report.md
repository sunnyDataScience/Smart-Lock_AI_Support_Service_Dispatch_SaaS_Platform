# 使用者研究報告 — Smart Lock AI 客服與派工 SaaS 平台

> 本報告回答：這個平台服務誰？四方角色各自是誰、痛點與目標是什麼、行為脈絡與成功定義為何？角色之間的期待落差如何被產品決策對齊？
> 下游文件：旅程細節見 [07_Journey_Map](./07_Journey_Map.md)；任務級流程見 [08_User_Flow](./08_User_Flow.md)；頁面組織見 [09_IA](./09_IA.md)。

---

## 1. 研究目的與方法

### 1.1 目的

智慧鎖售後服務長期依賴「老師傅的腦袋」：LINE 訊息湧入後由人工逐條詢問品牌、型號、地址，紙本記錄、Excel 對帳、電話催收；新客服要 3 個月才能上手，師傅、客戶、品牌方每月為對帳爭執。本研究盤點平台所有利害關係人，建立角色模型與 Persona，作為產品、設計、營運與架構團隊的共同人物設定基準。

### 1.2 方法

| 方法 | 說明 | 產出 |
|---|---|---|
| 桌面研究 | 智慧鎖售後服務領域（Chatlock / dormakaba 等一線品牌實體派工單）與 LINE 生態行為分析 | 派工單 6 模組領域知識、LINE 使用者行為假設 |
| 利害關係人盤點 | 依商業模式（License 授權、per-brand 部署、技師共享池）盤點所有接觸平台的角色 | §2 角色全景 |
| 角色場景推導 | 由業務流程（進線 → 處理 → 派工 → 現場 → 結算）推導各角色的任務情境 | §3 Persona 卡 |
| 衝突分析 | 攤開角色間的期待落差，逐條對齊到產品決策 | §5 落差對齊表 |

### 1.3 範圍聲明

- 本報告聚焦**平台四方角色 + 潛在加盟品牌**；品牌內部細分職能（客服、財務、稽核）以附錄形式收錄為次要角色。
- 量化行為數據（如各分群佔比、情緒量表）尚無實測來源，凡引用皆標 `[待確認]`。

## 2. 角色全景

平台角色以**四方 RBAC 模型**為權威定義（ADR-P006，deny-by-default enforce）：

| 角色 | 對象 | 範圍 | 帳號來源 | 主要進入點 |
|---|---|---|---|---|
| **終端客戶** | 智慧鎖消費者（LINE 用戶） | 自己的對話 / 報修案件 | LINE 帳號（免註冊） | LINE Bot（agent）+ token 公開頁（`/track` `/quotes` `/consent` `/scope-change`） |
| **品牌營運 — 派工小編** | 品牌自己的人 | 單一品牌租戶內操作（派工 / 工單 / 客服） | 租戶 Admin 開通 | Casdoor OIDC 登入 → dispatch portal（:3000） |
| **品牌營運 — 租戶 Admin** | 品牌方管理者 | 單一品牌租戶內 | Casdoor org admin，自助開通帳號給自己人 | Casdoor OIDC 登入 → dispatch portal（:3000） |
| **簽約師傅（技師）** | 現場鎖匠 | **跨租戶身分**（可服務多個品牌，由技師共享池管理） | Casdoor + 技師平台註冊審核 | Casdoor OIDC 登入 → 獨立師傅 web（technician-platform，:3001） |
| **平台管理員（Super Admin）** | 平台維運方 | **跨租戶**治理 | 平台建立 | Casdoor OIDC 登入 → 平台 console（:3003） |
| **潛在加盟品牌** | 尚未簽約的品牌商 | 公開申請面 | 無（申請時建立） | landing 導入頁（:3002）→ 品牌申請 → Casdoor License 開通 |

角色關係要點：

1. **技師是跨品牌身分**（ADR-P004）：一位鎖匠可服務多個品牌，身分 / 技能 / 認證 / 排班 / 佣金結算主體由技師共享池（technician-platform）單一真相管理，不屬於任何單一品牌。
2. **品牌租戶自助開帳**（ADR-P006）：租戶 Admin 在 Casdoor org 內自行開通派工小編帳號，平台方不介入品牌內人事。
3. **終端客戶無帳號**：全程以 LINE 身分互動，需要跨出 LINE 的操作（查看報價、簽署同意、追蹤進度）走簽章 token 公開頁，免登入。

### 內部次要角色（品牌租戶內細分，附錄）

品牌租戶內部依營運規模可再細分職能，這些職能在權限模型上收斂為「派工小編」與「租戶 Admin」兩個角色，差異由租戶內部分工與頁面可見性（見 [09_IA §9](./09_IA.md)）表達：

| 內部職能 | 收斂至 | 典型任務 |
|---|---|---|
| 客服人員 | 派工小編 | 進線監看、AI 接手、問題卡處理 |
| 客服主管 | 租戶 Admin | 報價審核、高風險 SOP 覆核、退款高額核准 |
| 派工調度 | 派工小編 | 派工佇列、媒合、改派 |
| 會計 / 財務 | 租戶 Admin | 對帳、退款雙簽、月結匯出 |
| 知識管理者 | 租戶 Admin | 知識庫 / SOP 草稿審核（knowledge-refinery 精煉流程） |

## 3. Persona 卡

> **本節是全平台唯一的 `PER-*` Persona 節點正典**（CR-0185）。`規格統控整理/_canon.py:load_personas()`
> 只讀這裡；`_relations/sc_embodies_persona.yaml` 宣告哪條 `SC` 體現哪個 `PER`，閉合追溯鏈
> 「誰」那一端：`PER → SC → {FR/NFR} → TC`。BDD 生成視圖的 `As a <persona>` 也取自這裡的名稱與
> 成功定義。改 Persona 事實只改本節，勿在別處另立第二份。
>
> ID 慣例：`PER-<分線>-NN`（`CUS/OPS/TEC/KNW/PLT` 對齊 `28_Scenarios` 五分線）。§3.1–3.4 為
> 四個主要 Persona；§3.5 為在 `SC` 中擔任主要/必要 Actor 的次要角色（附錄，欄位精簡）。

### 3.1 終端客戶 — 「被鎖在門外的林太太」

| 欄位 | 內容 |
|---|---|
| Persona ID | `PER-CUS-01` |
| 情境 | 晚上八點回家，智慧鎖沒電 / 感應失靈，被鎖在門外；唯一會用的工具是 LINE |
| 目標 | 立刻有人回應、用最少的來回把問題講清楚、盡快進家門 |
| 痛點 | 打客服電話沒人接；被反覆問品牌型號但根本不知道；報價不透明、到場才加價 |
| 行為脈絡 | LINE 上打字或直接拍照；急件時情緒激動、容忍度極低 |
| 成功定義 | 5 秒內看到 AI 回應；急件 5 分鐘內有真人接手；報價金額明確、確認後不被亂加價 |
| 對應系統 | agent（LINE Bot）、token 公開頁（quotes / consent / track） |

### 3.2 品牌營運（派工小編）— 「一個人盯全場的小美」

| 欄位 | 內容 |
|---|---|
| Persona ID | `PER-OPS-01` |
| 情境 | 品牌客服團隊 2-3 人，同時監看數十條 LINE 對話；AI 處理大多數進線，她只接例外 |
| 目標 | 只在 AI 處理不了時介入；問題卡一眼看懂案況；報價、派工、追蹤在同一個後台完成 |
| 痛點 | 不知道哪些對話需要接手；工單資訊分散（紙本 / Excel / 對話截圖）；退款與取消費規則靠記憶 |
| 行為脈絡 | 整天掛在 dispatch portal；依 WS 即時通知行動；高峰時段多工切換 |
| 成功定義 | 客服佇列清空；接手的每一單都有完整問題卡脈絡；取消費 / 退款分層由系統自動算，特殊情境可覆寫並留稽核 |
| 對應系統 | web dispatch portal（:3000）、api 控制平面 |

### 3.3 簽約師傅 — 「跑三個品牌的阿宏師傅」

| 欄位 | 內容 |
|---|---|
| Persona ID | `PER-TEC-01` |
| 情境 | 有鎖匠證照，同時簽約 2-3 個智慧鎖品牌；整天在外，手機是唯一工具 |
| 目標 | 一鍵接單、路線與時窗清楚、現場流程（拍照 / 加價 / 簽名）不用記在腦袋；月底一份對帳單看清跨品牌收入 |
| 痛點 | 各品牌各一套系統與帳號；到場才發現案件資訊錯誤（帶錯料、判錯保固）；對帳吵不完 |
| 行為脈絡 | 手機 PWA 使用；工地 / 移動中網路不穩；接單決策以距離、時窗、佣金為準 |
| 成功定義 | 一個帳號服務所有簽約品牌；派工推播 2 秒內到手；完工回報 5 分鐘內完成；跨品牌單一對帳單（statement）月結對得起來 |
| 對應系統 | technician-platform 獨立師傅 web（:3001）、OHS 媒合 + Kafka 事件（🔜 規劃中） |

### 3.4 平台管理員（Super Admin）— 「管十個品牌的維運者」

| 欄位 | 內容 |
|---|---|
| Persona ID | `PER-PLT-01` |
| 情境 | 平台方維運人員，負責品牌 onboarding、師傅認證審核、跨租戶治理與健康監控 |
| 目標 | 品牌申請 → License 開通 → provisioning 一條龍；師傅 KYC / 認證審核有佇列與 SLA；跨租戶問題一眼定位 |
| 痛點 | 品牌開通若靠手工建置易漏步驟；師傅認證材料分散；跨品牌事故無統一觀測面 |
| 行為脈絡 | 平台 console（:3003）+ SigNoz 可觀測性（🔜 規劃中）；低頻但高權限操作，全程需稽核 |
| 成功定義 | 品牌從申請到上線的 provisioning 全自動（🔜 規劃中）；師傅審核佇列不積壓；每一次跨租戶操作可追溯 |
| 對應系統 | 平台 console、Casdoor（IdP + 租戶 org + License）、technician-platform 審核面 |

### 3.5 次要角色 Persona（附錄）

> 以下角色在 `28_Scenarios` 中擔任某條 `SC` 的主要或必要 Actor，故需 `PER` 節點才能讓
> `sc_embodies_persona` 邊解析（V2）。權限模型上多數收斂至「派工小編／租戶 Admin」

| Persona ID | 角色 | 情境／目標 | 痛點 | 成功定義 |
|---|---|---|---|---|
| `PER-OPS-02` | 租戶 Admin（品牌管理者）| 單一租戶內自助開通小編帳號、審核報價與退款雙簽、跑月結七帳本對帳、必要時回滾品牌配置 | 對帳爭議靠人工；高風險操作缺集中審批 | 帳號自助開通免平台介入；月結 borrow=lend 對得起；每筆敏感操作留 SoD 稽核 |

| `PER-KNW-02` | Domain Expert（領域專家）| 在 knowledge-refinery 精煉流程審核事實正確性與 SOP 內容 | 長尾知識散落、來源可信度不一 | 僅經來源標註（provenance）且通過審核的知識可發布 |
| `PER-KNW-03` | Family Reviewer（安全覆核者）| 對高風險作業 SOP 做使用者視角的可讀性與安全第二關覆核 | 專業 SOP 對一般使用者不友善、潛在安全誤導 | 高風險 SOP 經第二關覆核、語意清楚且無安全誤導才發布 |
| `PER-PLT-02` | 潛在加盟品牌 | 從公開 landing 導入頁提出品牌申請、走 Casdoor License 開通上線 | 手工建置易漏步驟；不確定開通進度 | 申請 → License 開通 → provisioning 一條龍、進度可追蹤 |
| `PER-PLT-03` | DPO（資料保護官）| 代表 data subject 執行 GDPR 被遺忘權請求並確認合規銷毀 | legal-hold 與刪除衝突難判定；刪除是否徹底無稽核 | 被遺忘權 ≤7 天執行或發客戶通知；全程 append-only 稽核、硬刪有據 |

## 4. 終端客戶細分

終端客戶依報修頻率與價值再分四群，作為對話策略、優先級與測試資料設計的基準：

| 分群 | 特徵 | 產品應對 |
|---|---|---|
| **首次報修客戶** | 不熟 LINE Bot 互動、描述模糊、不知道品牌型號 | 漸進式引導 + 主動照片引導；問題卡完整度 gate（≥ 0.85）確保資料收齊才往下走 |
| **回頭客** | 有歷史案件（保固內送修 / 重複症狀）、期待被記得 | per-user 記憶（agent 記住設備與歷史）、保固狀態自動判定（RMA 延長規則） |
| **高價值客戶** | B2B 建商 / 品牌商案場、多設備、合約 SLA | 租戶維度隔離、建案批量設備管理、保固起算 = 點交日模式 |
| **高流失風險客戶** | 有取消 / 退款 / 爭議紀錄、負面情緒訊號 | 情緒偵測分流（怒客屬急件 4 類，bypass AI 直轉真人）、sentiment-alerts 監看頁供營運跟進 |

各分群量化佔比與 LTV 差異 `[待確認]`（尚無上線後行為數據）。

## 5. 利害關係人期待落差與對齊

角色間的期待衝突若不提前攤開，會在上線後以客訴與合約爭議形式爆發。以下 7 組衝突已逐條對齊到產品決策：

| # | 衝突點 | A 立場 | B 立場 | 對齊決策 |
|---|---|---|---|---|
| 1 | AI 自助 vs 越權風險 | 品牌方要自助解決率 ≥ 60%（省客服人力） | 品牌營運怕 AI 越權承諾（免費保固 / 亂建單） | 自助率 KPI + 轉真人率 counter-metric 雙軌；AI 越權硬規則（不可自行建單、不可承諾免費保固），guardrail 系統攔截 |
| 2 | 報價 final vs range | 終端客戶要明確數字 | 品牌方 / 法務永禁 AI 給 final 價（防越權） | AI 只給範圍價（range）；final 報價由品牌營運審核後經 token 公開頁 `/quotes` 送客戶確認 |
| 3 | SOP 入庫速度 vs 品質 | 營運要新 SOP 快上線 | 知識審核方要雙審把關 | 知識精煉走 knowledge-refinery 獨立服務：AI 產 draft → 人工審核後才寫入（事實 → pgvector 語料、行為 → skill），高低風險分流審核 |
| 4 | 取消費系統自判 vs 人工覆寫 | 系統依工單狀態自動算 5+1 階段取消費 | 營運遇特殊情境（不可抗力、客訴補償）要覆寫 | 全階段派工小編可覆寫 + 強制留 audit log；師傅發起取消另有首次免責 / 重複扣款 / 不可抗力憑證三軌 |
| 5 | 證據（Evidence）可見性廣度 | 平台治理面要看全部 | 客戶不應看到內部成本拆分；品牌不應看到他牌資料 | 角色 × 案件生命週期可見性矩陣：客戶只見總額 / 實收；成本拆分（品牌價 / 師傅成本 / 佣金）限品牌營運內部；跨品牌一律隔離 |
| 6 | 個資保留寬鬆 vs 嚴格 | 法務要求嚴格刪除（被遺忘權 7 天內處理） | 營運與知識面要長期歷史學習 | 分層保留：一般案件 1 年 / RMA +3 年 / 匿名化知識永久 / 被遺忘權兩階段刪除（金鑰銷毀軟刪 → 30 天硬刪），與 legal-hold 衝突時拒絕並限期通知 |
| 7 | 租戶隔離 vs 跨品牌洞察 | 品牌方要絕對隔離（一品牌一庫，物理隔離） | 平台方想做跨品牌 BI 與技師調度 | per-brand bundle 物理隔離（ADR-P005）為底線；跨品牌僅限技師共享池（ADR-P004，經 OHS API + 事件，品牌不直連技師庫）與匿名化統計 |

## 6. 關鍵洞察與設計原則

由 §3–§5 收斂出四條貫穿全產品的設計原則：

1. **自助優先、真人兜底**：AI 是第一線（三層解決：案例庫 → 手冊 RAG → 轉真人），但急件 4 類（鎖外 / 內困 / 安全風險 / 怒客）bypass 所有自助層，5 分鐘內強制轉真人。自助率是效率指標，不是擋真人的藉口。
2. **AI 越權邊界是產品底線**：AI 不建單（一律人工 1-click gate）、不給 final 價（只給 range）、不承諾保固減免。所有邊界由系統 guardrail 攔截，不靠 prompt 自律；品牌自服務調校（Agent Configuration Studio，ADR-P013）採受保護層 + 客製層分層，escalation 與 domain-safety 規則品牌不可 override。
3. **角色最小權限、deny-by-default**：四方角色經 Casdoor OIDC 發角色 claim，api 端 resource-level `role_required` 實際阻擋（ADR-P006）；前端 gate 僅為 UX 分站與導覽過濾，不是授權邊界。
4. **技師是跨租戶的一等公民**：師傅端不塞進任何品牌後台——獨立師傅 web + 技師共享池單一真相（ADR-P004 / ADR-P005），一個帳號服務多品牌，跨品牌單一對帳；這是師傅留存（生態關鍵角色）的核心體驗承諾。
