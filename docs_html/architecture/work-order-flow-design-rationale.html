標準化派工單流程設計說明

一句話：把「派工門檻」「現場蒐集」「法律簽署」「計費核銷」拆成各自階段， 讓對的角色在對的時間填對的欄位，而不是逼一個人一次填完一張他根本還不知道答案的單子。

本文件說明電子鎖客服 / 派工平台中，問題卡 → 開單 → 工單這條主流程為何如此設計， 以及工單管理頁的「標準化派工單（6 模組）」如何對齊 20260617資料/電子鎖安裝與維修派工單整合分析報告.pdf（以下簡稱「分析報告」）。

一、背景：分析報告的 6 大模組

分析報告整合 Chatlock 與 dormakaba 兩家一線品牌的實體派工單，歸納出一套標準化派工單應含的 6 大功能模組：

# 模組 設計核心
1 基礎案件資訊 客戶與履約辨識（誰／何地／何時）
2 設備與環境辨識 環境與硬體界定（型號／序號／門材質／遮雨）
3 工單類型與狀態管理 服務屬性與結案依據（新裝／保內／保外、完工狀態）
4 施工說明與免責合規 法律風險防範（拓孔／鑽洞、破壞鎖、個資授權簽名）
5 多維度計費與核銷 透明化計費結構（出勤／安裝／破壞／零件／總計）
6 雙方責任簽認 驗收與款項確認（工程師 + 客戶簽名）

分析報告的三大目標：法律風險防範、結案 / KPI 依據、減少現場收費爭議。 下文說明的流程設計，正是為了達成這三個目標而切。

二、完整流程

① 問題卡（AI 從 LINE 對話生成，status: draft）
     │  「確認問題卡」→ status: draft → confirmed
     │  （三層解決：L1 AI 直接回 / L2 遠端指導 / L3 才現場派工）
     ▼
② 開單（ConvertModal）── 填「3 個聯絡欄位」，不是 6 模組
     │  · 服務地址 *（必填：AI 草擬卡無地址，客服 HITL 補）
     │  · 聯絡人（選填）
     │  · 聯絡電話（選填）
     │  ⚠ 完整度 gate：問題卡缺 品牌/型號/症狀/急迫度 → 422，
     │     需主管填「強制開單原因」override
     ▼
③ 工單管理 /work-orders/[id]「標準化派工單（6 模組）」← 對齊分析報告
        模組 1/2/3/5 標準欄位可內嵌編輯；4/6 與部分欄位唯讀

⚠ 常見誤解：「開單填的 3 個欄位」≠ 對齊分析報告的資訊。 開單那步（ConvertModal）只填地址/聯絡人/電話，純粹是「建立工單的最低門檻」。 真正對齊分析報告 6 模組的是第 ③ 步的 DispatchOrderView。

三、設計用意（為什麼這樣切）

用意 1：漸進式資料蒐集 —— 在「自然產生的那一刻」由「知道它的角色」填

若一開始就把 6 模組全攤開要客服填完才能開單，結果一定是客服瞎猜或全部留空，因為：

  • 開單當下（客服階段）根本不知道序號、門厚、遮雨、要不要破壞鎖、零件多少錢 —— 這些是技師到現場才會知道的。
  • 計費明細是報價 / 完工階段才產生的。
  • 客戶同意簽名是客戶本人在 LINE 上才做得到的。

所以系統把資料蒐集攤平到生命週期各階段： 開單（客服）→ 派工（調度）→ 現場（技師）→ 完工回報 → 計費 → 客戶簽收。 每個欄位在它「該被知道」的時候才填。

用意 2：問題卡 / 工單分離 —— 大多數問題卡根本不會變工單

問題卡是診斷 / 分流階段（三層解決：L1 AI 直接回 / L2 遠端指導 / L3 才現場派工）。 只有 L3 需要派人到現場的才開單。

若不分離、每通客訴都直接生工單，後台會被一堆「其實 AI 一句話就解決」的假工單淹沒。 分離之後，工單列表裡每一張都是「真的要派車出去」的 —— 這也是工單上那些物流 / 調度欄位 （地址、技師、排程）有意義的前提。

用意 3：開單最低門檻 + 完整度 gate —— 派工門檻，不是資料蒐集

開單那步只要 地址（必填）+ 聯絡人 / 電話，因為派工的最低需求就是「去哪裡、找誰」。 地址必填是因為 AI 草擬卡沒地址（對話裡客戶不一定講），必須客服 HITL 補（CR-0022）。

同時擋一道完整度檢查（缺品牌 / 型號 / 症狀 / 急迫度 → 422，需主管填 override 原因，CR-0042）—— 用意是把「垃圾工單」擋在派工之前：沒有品牌型號，技師到現場帶錯料、判錯保固。 留 override 是給「客戶現場急修」的例外逃生門。

用意 4：唯讀 vs 可編輯 —— 法律效力 + 防止資料打架

對應分析報告的「施工與責任釐清」與「法律合規」：

為什麼唯讀 原因
模組 4 免責同意（走 LINE 簽） 拓孔 / 破壞鎖 / 個資授權有法律效力，簽名必須是客戶本人做，後台代簽 = 無效。後台只能看狀態。
模組 6 簽認 同理，簽名是現場 / 客戶端完成，後台不能偽造。
維修原因（源自問題卡）、完工狀態、費用明細（來自報價） single source of truth —— 同一筆資料只有一個地方能改，避免兩處可編輯造成金額 / 狀態對不上（對齊 .claude/rules/coding-style.md 不可變 / single-source 治理）。

六、為什麼不「一次填完」

一次填完看似簡單，但會犧牲掉分析報告要的三個目標：

  • 法律風險：免責 / 個資簽名若能在後台一次填完 = 可代簽 = 無法律效力。
  • 計費爭議：費用若在開單時憑空填，而非由現場報價產生，金額無來源、不可稽核。
  • KPI / 結案：完工狀態若可在任何階段隨意改，結案數據失真。

漸進蒐集 + 唯讀防偽 + 完整度 gate，才是達成這三個目標的設計骨架。
