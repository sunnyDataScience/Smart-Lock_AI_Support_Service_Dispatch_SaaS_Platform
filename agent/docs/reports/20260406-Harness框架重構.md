# Harness 框架全系統重構 — 2026-04-06

根據 2026-04-04 架構討論會議決議，將整個系統從純 RAG 模式重構為 8 層 Harness 框架包覆架構。硬體故障走收斂式推理引擎（Fault Tree），非故障查詢走 RAG，全部在 Harness 框架底下運作。

---

## 1. Graph Flow 重構

### 問題

原有 V1.0 流程為線性 RAG 管線，所有查詢（包括硬體故障）都走 Router → Agent → pgvector 檢索，缺乏結構化診斷推理能力。遇到複雜故障時無法透過追問收斂，只能轉接真人。

### 解決方案

依照 `docs/agent-harness-refactor/graph-flow-redesign.md` 規範，將 Graph 重構為 Harness-aware 架構：

**舊流程：**
```
START → pre_process → manage_memory → rewrite_query → router → [agents]
      → merge_answers → update_profile → post_process → END
```

**新流程：**
```
START → pre_process → manage_memory → rewrite_query → task_decompose [L1]
      → context_assemble [L2] → safety_gate [L6]
      → {diagnostic_respond | router → [agents]}
      → merge_answers → verify_answer [L5]
      → update_profile → entropy_check [L8] → post_process → END
```

新增 3 個條件分支：
- `safety_gate` 三向分流：診斷收斂 → `diagnostic_respond`（跳過 RAG）| 正常 → `router` | 安全攔截 → `post_process`
- `verify_answer` 品質迴路：通過 → `update_profile` | 不足 → `context_assemble`（retry）
- `router` fan-out 不變

### 效果

- 硬體故障走診斷推理引擎，不經過 RAG，回應更精準
- 非硬體查詢經 Harness 各層包覆後走 RAG，流程不變
- 所有行為由 config.toml 開關控制，可逐層啟停

## 2. 8 層 Harness 節點實作

### L1 Task Decompose — 診斷推理引擎

修復 `decomposer.py` 的 LLM 注入問題（原本從 `config["configurable"]` 取 LLM，但無處注入）。改為直接 import `get_llm(LLM_CONFIG)`。

新增非硬體查詢早退機制：LLM 輸出 `is_hardware_fault: false` 時，設定 `task.intents` 後直接返回，由 Router 做 config lookup 派發。

### L2 Context Assembly — Freshness + Token Budget

從 skeleton 實作為完整功能：freshness 評分、token budget 計算、retry 調整。V1.0 設為 `assemble_enabled = false`（latency concern）。

### L3 Tool Governance — Agent Subgraph Middleware

在 `agents/__init__.py` 的 `execute_tools` 中加入 governance middleware：
- Pre-execution：驗證工具參數、檢查風險等級（read/write/escalate）
- Post-execution：截斷超過 3000 字的結果，防止灌爆 context

### L5 Feedback Verifier — 品質評估 + Retry

從 skeleton 實作為 LLM 品質評分（completeness 0.3 + accuracy 0.3 + safety 0.2 + actionability 0.2）。V1.0 設為 `verify_enabled = false`。

### L6 Safety Gate — 已存在

原有實作已涵蓋危險指令偵測、PII 偵測、情緒分析、Red_Code 緊急升級。本次加入條件邊（`requires_approval` → 直接跳到 `post_process`）。

### L7 Observability — @traced 全面接線

所有 12 個 graph 節點套用 `@traced` 裝飾器，自動記錄 node_name、timestamp、duration_ms、diagnosis_status。

### L8 Entropy Check — 新案例偵測

從 skeleton 實作為新案例偵測：比對故障樹匹配結果，低信心度假設標記為 `is_novel = True`，加入 SOP 候選佇列。

### diagnostic_respond — 診斷短路節點

新增節點，將 `task.diagnostic_context` JSON 轉為使用者友善回覆：
- `verifying` → 提取追問問題
- `conclusion_ready` → LLM 格式化修復步驟
- `dispatch_recommended` → LLM 格式化派工建議

## 3. Confidence Score 累積 + 品牌元件樹

### Confidence Score

`DiagnosticContext` 新增 `confidence_score`（累積信心值）和 `confidence_threshold`（閾值 0.75）。每輪驗證追問後，從 LLM 輸出的 `confidence_update.confidence_gain` 累加。達到閾值時 `resolve_next_state()` 直接返回 `CONCLUSION_READY`，不再追問。

### 品牌專屬元件樹

`components.toml` 新增 `[brand_overrides]` 區段，支援 dormakaba / Kaadas / Philips / Milre 各品牌的錯誤碼和派工信號。`KnowledgeLoader.get_component_graph(brand=)` 在 runtime 合併覆蓋。

## 4. 規範差距修正

對照 `docs/agent-harness-refactor/` 規範文件進行 gap analysis 後修正 4 項缺口：

### ProblemCard 正式整合

原本 `decomposer.py` 把 ProblemCard 當普通 dict 操作。修正後正式建立 `ProblemCard` dataclass（`card_id = "pc_{uuid8}"`），每輪呼叫 `calculate_completeness()` 計算分數。

| 場景 | completeness_score |
|------|-------------------|
| 完整卡（symptom + category + brand + model） | 0.78 |
| 最小卡（僅 symptom） | 0.30 |
| 空卡 | 0.0 |
| 全欄位 | 1.0 |

### rewrite_query 恢復接線

第一階段移除了 `rewrite_query` 導致非硬體查詢失去口語改寫能力。已恢復接線：`manage_memory → rewrite_query → task_decompose`。

### ResolutionAttempt 追蹤

L5 `verify_answer` 品質評分後建立 ResolutionAttempt dict（timestamp, agent_name, strategy, result, answer_snippet, quality_score），附加到 `problem_card.attempts`。

### V1.0 關閉 L2/L5

依照 `optimization-strategy.md` 建議，V1.0 關閉 L2 Context Assembly 和 L5 Feedback（各增加 2-5s latency）。Graph 結構不變，節點內部 pass-through。
