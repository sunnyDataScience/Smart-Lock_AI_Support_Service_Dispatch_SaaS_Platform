# 20260408 — 對話品質修復：記憶失效、意圖誤分類、多模態競態、架構分層

基於實際客服對話測試（電子鎖指紋沒反應場景），發現 AI 重複回答、忽略用戶修正、意圖分類錯誤、多模態處理失效等系統性問題，本次集中修復。

---

## 1. 對話記憶失效 — Agent 滑動窗口（`8a9c864`）

### 問題

`builder.py:route_by_intent()` 在派發 agent 時，只傳遞 `SystemMessage（摘要）+ 當前問題`，**丟棄了所有歷史 human/ai 對話**。Agent 每輪都像第一次聽到問題，導致：

- 「電池沒電」建議被重複 6 次
- 用戶說「我電池還有電啊」後 AI 繼續講電池
- `manage_memory` 閾值 50 條，短對話根本不觸發壓縮，`summary` 為空

### 修復

在 `route_by_intent()` 中加入滑動窗口，從 `state["messages"]` 中擷取最近 N 輪 human/ai 對話（排除 tool messages 和當前問題），與 summary + 當前問題一起傳給 agent。

### 設定對齊

```toml
max_messages_threshold = 50    # 超過 50 條才觸發壓縮
context_retention_pair = 20    # 壓縮後保留 20 輪
router_context_pairs   = 20   # agent 看到全部保留的 20 輪（原本是 3，且未被使用）
```

### 影響範圍

- `agent/graph/builder.py` — `route_by_intent()` 重寫
- `agent/config.toml` — `router_context_pairs` 3 → 20

## 2. 意圖分類錯誤 — Prompt 明確排除清單（`4c8ede3`）

### 問題

`diagnostic_reasoning.md` 的 `is_hardware_fault` 判斷規則過於模糊，排除清單只有「store info, APP settings, greetings, pricing, manual requests, out-of-domain」，**沒有提到「個人資料更新」**。

LLM 在滿篇硬體診斷 context 中傾向把「更新地址：台北市」判為硬體問題 → `intents: ["hardware_tech"]` → 路由到硬體技師 agent → 回覆又是電池建議。

### 修復

- **Rule 14 (is_hardware_fault)** — 明確列出 8 類排除項目（個人資料更新、問候、門市查詢、App 操作、說明書、費用、轉接、非相關），每類附中文範例。加上 `IMPORTANT` 提醒：即使之前在聊硬體問題，新訊息若為非技術請求仍應判 `false`。
- **Rule 15 (intent_classification)** — 每個 intent 附帶中文範例，特別是 `general_reception` 明確包含「更新地址、更新電話、修改個人資料」。

### 影響範圍

- `agent/harness/task/prompts/diagnostic_reasoning.md` — Rule 14-15 重寫

## 3. 多模態競態條件（`1f729c1`）

### 問題

三個 bug 導致多模態處理形同虛設：

| Bug | 現象 |
|-----|------|
| **競態條件** | 用戶傳文字 + 照片 → debounce 1.5s 後觸發，但 Flash-Lite 要 3-5s，照片描述來不及注入 |
| **佔位殘留** | 即使加了佔位訊息，debounce 超時時「處理中...」會被送進 LLM |
| **錯誤 fallback** | 媒體處理失敗 → 發送 `get_sticker_reply()`（「收到您的貼圖了」）— 語意完全錯誤 |

### 修復

1. **佔位 → 替換機制**：媒體訊息到達時立即在 buffer 插入佔位（重設 debounce timer），Flash-Lite 完成後用 `replace_media_placeholder=True` 替換佔位文字
2. **媒體等待**：debounce `process_and_reply()` 偵測到佔位時額外等待最多 10s（每 0.5s 輪詢）
3. **fallback 改善**：失敗時注入「系統無法辨識內容，請根據對話脈絡盡量協助」而非貼圖回覆
4. **reply_token 分離**：`_handle_media_message` 不再持有 reply_token，由 debounce 統一管理

### 修復後流程

```
用戶傳文字 → buffer=["文字"], timer=1.5s
用戶傳照片 → buffer=["文字", "[正在傳送圖片，處理中...]"], timer 重設
             → 背景: Flash-Lite 處理中...
1.5s 到    → debounce 偵測到佔位 → 額外等待
3s 後      → Flash-Lite 完成 → 替換佔位 → buffer=["文字", "[圖片描述]"], timer 重設
1.5s 到    → debounce 觸發 → 送 "文字\n[圖片描述]" 給 LangGraph
```

### 影響範圍

- `agent/app.py` — `_handle_media_message()` 重寫、webhook 媒體處理改用佔位
- `agent/core/debounce.py` — `add_message_to_buffer()` 加 `replace_media_placeholder` 參數、`process_and_reply()` 加媒體等待邏輯

## 4. 架構分層 — ProblemCard 搬到 Domain 層（`515760c`）

### 問題

`ProblemCard` 和 `DiagnosticStateMachine` 是業務領域模型，放在 `harness/task/` 下造成概念混淆。兩者零 harness 內部依賴，可以乾淨分離。

### 修復

```
agent/
├── domain/                              # 新建：業務領域模型
│   ├── problem_card.py                  # ← harness/task/
│   └── diagnostic_state_machine.py      # ← harness/task/
├── harness/
│   └── task/
│       ├── decomposer.py               # 編排引擎（留在 harness）
│       └── knowledge_loader.py          # 知識載入（留在 harness）
```

3 個檔案共 6 行 import 更新，59 項測試全部通過。
