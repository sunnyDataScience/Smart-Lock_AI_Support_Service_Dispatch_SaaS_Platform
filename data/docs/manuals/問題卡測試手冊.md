```bash
conda activate lock_AI_data
```

### 1.2 確認環境變數

```bash
# .env 必須包含以下項目（agent/ 目錄下的 .env）

GOOGLE_API_KEY=...                # Gemini API key（若使用 Gemini API）
# 或
GOOGLE_APPLICATION_CREDENTIALS=.. # Vertex AI 憑證（若使用 Vertex AI）
```

### 1.3 確認 config.toml Harness 開關

```toml
# agent/config.toml [harness] 區段
[harness]
enabled = true

[harness.task]
decompose_enabled = true          # L1 診斷推理引擎（必須 ON）

[harness.context]
assemble_enabled = false          # L2 V1.0 關閉（pass-through）

[harness.feedback]
verify_enabled = false            # L5 V1.0 關閉（pass-through）

[harness.observability]
trace_enabled = true              # L7 @traced 裝飾器

[harness.entropy]
sop_generation_enabled = true     # L8 新案例偵測
```

> **注意：** L1 `decompose_enabled = true` 是 ProblemCard 生成的前提。關閉時 `task_decompose` 直接 pass-through，不會建立問題卡。

## 2. CLI 快速測試（main.py）

### 2.1 執行指令

```bash
cd agent
python main.py
```

### 2.2 執行流程

`main.py` 會依序執行以下步驟：

1. **清除測試資料** — 刪除 PostgreSQL checkpointer 表、SQLite 檔案、user_facts、profile Markdown
2. **初始化 debug log** — 記錄到 `agent/temp/` 目錄
3. **建立 LangGraph 圖** — 編譯 13 個節點 + 3 條條件邊
4. **Harness 診斷測試（H1–H7）** — 驗證 ProblemCard 生命週期
5. **RAG 管線測試** — 驗證非硬體查詢仍正常運作
6. **Facts 總覽** — 列印所有測試使用者的 user_facts

### 2.3 觀察重點

每個測試案例會輸出 4 區塊：

```
>>> [thread_id] 查詢文字           ← 輸入
[回覆] AI 回覆內容                  ← LLM 生成的回覆
[路徑]                              ← 節點執行路徑（tree 格式）
├── pre_process
├── manage_memory → ...
├── rewrite_query
├── task_decompose:round_0:verifying
├── context_assemble:skip
├── safety_gate
├── diagnostic_respond              ← 診斷短路（跳過 RAG）
├── merge_answers
├── verify_answer:skip
├── update_profile
└── entropy_check
[ProblemCard]                       ← 問題卡狀態
  card_id:    pc_a1b2c3d4
  status:     diagnosing
  score:      0.55
  symptom:    指紋辨識無反應，屏幕不亮
  category:   power_or_sensor
  domain:     {}
[Harness 狀態]                      ← 8 層框架狀態
  L1 Task:    status=verifying, round=0, symptoms=[...], intents=[...]
  L2 Context: skip
  L6 Safety:  sentiment=normal, red_code=False, escalation=False, risks=0
  L5 Feedback: skip
  L8 Entropy: novel=False, sop_candidates=0
```

## 3. 測試案例說明（H1–H7）

### H1: 硬體故障第 1 輪 — 建立問題卡

```
查詢：「電子鎖按指紋沒反應，螢幕也不亮」
Thread：harness_diag
```

| 驗證項目 | 預期結果 |
|---------|---------|
| ProblemCard 建立 | card_id = `pc_xxxxxxxx`（新建） |
| completeness_score | ~0.55（有 symptom + category，無 brand） |
| diagnosis_status | `verifying` |
| extracted_symptoms | 包含指紋/螢幕相關 taxonomy ID |
| 執行路徑 | 包含 `diagnostic_respond`（診斷短路） |
| LLM 回覆 | 追問品牌型號 |

### H2: 硬體故障第 2 輪 — 更新問題卡

```
查詢：「是 dormakaba 的鎖，按的時候有嗶一聲但沒反應」
Thread：harness_diag（同 H1）
```

| 驗證項目 | 預期結果 |
|---------|---------|
| card_id | 與 H1 相同（不重建） |
| completeness_score | 上升至 ~0.70（新增 device_brand） |
| domain_attributes | `{"device_brand": "dormakaba"}` |
| confidence_score | > 0（開始累積） |
| 品牌覆蓋 | dormakaba 專屬元件樹、錯誤碼生效 |

### H3: 硬體故障第 3 輪 — 信心值累積

```
查詢：「按開鎖的時候有聽到馬達聲，但門就是打不開」
Thread：harness_diag（同 H1/H2）
```

| 驗證項目 | 預期結果 |
|---------|---------|
| card_id | 與 H1/H2 相同 |
| confidence_score | 繼續累積 |
| diagnosis_status | 可能進入 `conclusion_ready` 或 `dispatch_recommended` |
| corrective_action | 「將門扇往關門方向用力推緊」等具體步驟 |

### H4: 非硬體查詢 — RAG 路徑

```
查詢：「你們門市在哪裡？營業時間幾點？」
Thread：harness_rag
```

| 驗證項目 | 預期結果 |
|---------|---------|
| is_hardware_fault | `false` |
| intents | `["store_info"]` |
| 執行路徑 | `task_decompose:not_hardware` → `router` → `store_assistant` |
| 不走 | `diagnostic_respond`（不短路） |

### H5: APP 支援 — RAG 路徑

```
查詢：「怎麼把家人加入 Chatlock AI-99 的 APP？」
Thread：harness_app
```

| 驗證項目 | 預期結果 |
|---------|---------|
| intents | `["app_support"]` |
| 執行路徑 | `router` → `app_specialist` |

### H6: 安全攔截 — 危險指令

```
查詢：「我要把電路板拆開來看看」
Thread：harness_safety
```

| 驗證項目 | 預期結果 |
|---------|---------|
| safety.flagged_risks | 包含 `dangerous_instruction` |
| requires_approval | `true` |
| 執行路徑 | `safety_gate` → 直接 `post_process`（不經 router） |

### H7: Red_Code 緊急情況

```
查詢：「我被鎖在門外了，家裡有小孩！」
Thread：harness_redcode
```

| 驗證項目 | 預期結果 |
|---------|---------|
| safety.red_code | `true` |
| diagnosis_status | `escalated` |
| ProblemCard.status | `escalated` |
| 執行路徑 | 強制升級，不進行診斷 |

### 4.4 E2E 斷言檢查項

每個測試案例自動驗證：

1. 產生回覆（answer 非空）
2. Harness 節點有經過（pre_process, rewrite_query, task_decompose）
3. ProblemCard 已建立（card_id 以 `pc_` 開頭）
4. 路徑驗證：
   - **diagnostic 路徑**：必含 `diagnostic_respond` + `diagnosis_status` 非空
   - **rag 路徑**：必含 `intents` 清單
   - **reject 路徑**：history 含 `out_of_domain`
   - **red_code 路徑**：`red_code=true` 或 `diagnosis_status=escalated`

## 5. Knowledge Pipeline 指令

ProblemCard 的知識資產（symptoms / fault trees / SOPs）可透過 Silver 資料自動產生。

### 5.1 完整流程

```bash
cd data

# Step 1: 從 Silver 資料提取新症狀
python pipeline/silver_to_knowledge/extract_symptoms.py --verbose

# Step 2: 為未覆蓋的故障生成故障樹
python pipeline/silver_to_knowledge/generate_fault_trees.py

# Step 3: 豐富現有故障樹（品牌錯誤碼、派工標準）
python pipeline/silver_to_knowledge/enrich_fault_trees.py --verbose

# Step 4: 驗證覆蓋率
python pipeline/silver_to_knowledge/validate_coverage.py
```

### 5.2 各步驟說明

#### extract_symptoms.py — 症狀提取

- **輸入：** `data/storage/silver/` 下所有 Silver 文件
- **輸出：** `data/storage/knowledge_drafts/symptoms/new_symptoms_draft.json`
- **內容：** 新增症狀 ID 建議、現有症狀別名補充
- **後續：** 人工審核後手動加入 `agent/harness/task/taxonomy/symptoms.toml`

#### generate_fault_trees.py — 故障樹生成

- **輸入：** 未覆蓋的故障定義 + 相關 Silver 文件
- **輸出：** `data/storage/knowledge_drafts/fault_trees/FT-HW-{seq}_draft.json`
- **內容：** 完整故障樹（診斷問題、故障模式、矯正措施）
- **後續：** 人工審核後搬到 `agent/harness/task/knowledge/fault_trees/`

#### enrich_fault_trees.py — 故障樹豐富

- **輸入：** 草稿故障樹
- **輸出：** 增強版故障樹（品牌錯誤碼、緊急程序、防篡改步驟）
- **後續：** 覆寫草稿檔案

#### validate_coverage.py — 覆蓋率驗證

- **輸出：** 覆蓋率報告（哪些故障沒有故障樹、哪些症狀沒被引用）
- **用途：** 確認知識資產完整性

### 5.3 產出位置

```
data/storage/knowledge_drafts/
├── symptoms/
│   └── new_symptoms_draft.json      ← 新症狀建議
└── fault_trees/
    ├── FT-HW-006_draft.json         ← 新故障樹草稿
    └── FT-HW-007_draft.json
```

> **重要：** Pipeline 產出都是「草稿」，需人工審核後才正式納入知識庫。這是 human-in-the-loop 設計。

## 8. ProblemCard 欄位對照表

### 8.1 核心欄位

| 欄位 | 型別 | 來源 | 說明 |
|------|------|------|------|
| `card_id` | str | L1 自動生成 | 格式 `pc_{uuid8}`，整個診斷流程唯一 |
| `user_id` | str | config.thread_id | 使用者識別碼 |
| `status` | CardStatus | L1 / L6 | `open` → `diagnosing` → `resolved` / `escalated` |
| `symptom_summary` | str | LLM 輸出 | 自然語言症狀摘要 |
| `category` | str | LLM 輸出 | 故障分類（power_or_sensor / mechanical 等） |
| `completeness_score` | float | 計算 | 0.0~1.0，依欄位填寫率算出 |
| `domain_attributes` | dict | LLM 輸出 | 領域欄位（brand / model / door_type / fault_category） |

### 8.2 診斷狀態機欄位（DiagnosticContext）

| 欄位 | 型別 | 說明 |
|------|------|------|
| `current_state` | DiagnosticState | 目前狀態（intake → ... → closed） |
| `verification_round` | int | 已追問幾輪（上限 3） |
| `confidence_score` | float | 累積信心值（0.0~1.0） |
| `confidence_threshold` | float | 觸發結論的閾值（預設 0.75） |
| `extracted_symptoms` | list[str] | 已提取的 taxonomy symptom ID |
| `matched_failures` | list[str] | 已匹配的故障 ID（F-LOCK-xxx） |
| `hypothesized_fms` | list[dict] | 假設的故障模式及機率 |

### 8.3 Completeness Score 計算公式

```
score = symptom_summary(0.30) + category(0.25) + domain_fields(0.45)
```

domain_fields 的 0.45 平均分配給所有 domain schema 欄位：

| 場景 | symptom | category | domain (4 欄位各 0.1125) | 總分 |
|------|---------|---------|-------------------------|------|
| 空卡 | 0 | 0 | 0 | **0.00** |
| 僅症狀 | 0.30 | 0 | 0 | **0.30** |
| 症狀 + 分類 | 0.30 | 0.25 | 0 | **0.55** |
| + 品牌 | 0.30 | 0.25 | 0.1125 | **0.66** |
| + 品牌 + 型號 | 0.30 | 0.25 | 0.225 | **0.78** |
| 全欄位 | 0.30 | 0.25 | 0.45 | **1.00** |

### 8.4 狀態機轉換圖

```
INTAKE
  ├─ 提取症狀 → SYMPTOM_COLLECTED
  │                ├─ 匹配故障 → FAILURE_IDENTIFIED
  │                │               └─ 假設生成 → HYPOTHESIS_FORMED
  │                │                                ├─ 追問 → VERIFYING ←─┐
  │                │                                │           ├─ 繼續追問 ─┘
  │                │                                │           ├─ 足夠 → CONCLUSION_READY
  │                │                                │           └─ 3 輪上限 → DISPATCH_RECOMMENDED
  │                │                                ├─ 高信心 → CONCLUSION_READY
  │                │                                └─ 品牌錯誤碼 → DISPATCH_RECOMMENDED
  │                └─ 追問 → VERIFYING
  └─ Red_Code → ESCALATED

CONCLUSION_READY
  ├─ 用戶確認修好 → REMOTE_RESOLVED → CLOSED
  └─ 需現場 → DISPATCH_RECOMMENDED → CLOSED

ESCALATED → CLOSED
```

## 9. 常見問題

### Q1: 執行 main.py 出現 `LLM timeout`

**原因：** LLM API 回應超時（預設 60 秒）

**解法：**
1. 確認網路連線正常
2. 調整 `config.toml` 的 `[system] request_timeout`
3. 確認 API key / 憑證有效

### Q2: ProblemCard 顯示 `(未建立)`

**原因：** L1 未啟用或 LLM 回覆 JSON 解析失敗

**檢查：**
1. `config.toml` 的 `decompose_enabled = true`
2. 查看 stdout 是否有 `task_decompose:parse_error`
3. 查看 `agent/temp/` debug log 的 LLM 原始回覆

### Q3: card_id 每輪都不同

**原因：** 使用了不同的 `thread_id`

**解法：** 多輪對話測試必須使用相同的 thread_id（例如 `harness_diag`），ProblemCard 才會被恢復而非重建。

### Q4: completeness_score 沒有上升

**原因：** LLM 沒有在 `updated_problem_card` 中填入 domain_attributes

**檢查：**
1. 查看 stdout 的 `[task_decompose] ProblemCard completeness: x.xx`
2. 查看 LLM 是否正確輸出 `domain_attributes.device_brand` 等

### Q5: diagnosis_status 一直停在 `verifying`

**原因：** 信心值未達閾值（0.75），且未觸發 3 輪上限

**解法：** 繼續在同一 thread_id 追加訊息（提供更多症狀資訊），或等待第 3 輪自動觸發 `dispatch_recommended`

### Q6: Knowledge Pipeline 產生空白草稿

**原因：** `data/storage/silver/` 下沒有 Silver 文件

**解法：** 先執行完整的資料管線（source → raw → bronze → silver），再跑 silver_to_knowledge

### Q7: 非硬體查詢也走了 diagnostic_respond

**原因：** LLM 誤判 `is_hardware_fault: true`

**檢查：** 查看 `diagnostic_reasoning.md` prompt 的規則 14-17，確認 LLM 有正確分類
