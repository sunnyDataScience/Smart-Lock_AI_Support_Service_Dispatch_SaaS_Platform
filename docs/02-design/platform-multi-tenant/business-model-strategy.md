# Business Model & Deployment Strategy

> **文件狀態：策略文件（V3.0 規劃）**
> 多租戶 vs 賣斷 vs Hybrid 的商業模式分析，含市場案例與階段性建議。
> 建立日期：2026-04-21

---

## 1. 三種部署模式比較

```
模式 A：單租戶（現狀）
+=====================+
|   鎖市的系統         |   <-- 一套系統，一家店用
|   鎖市的資料         |
|   鎖市的 LINE OA     |
+=====================+


模式 B：多租戶 SaaS（規劃方向）
+===============================================+
|           平台（一套系統）                      |
|                                               |
|  +---------+ +---------+ +---------+          |
|  | 鎖市    | |台北鎖王 | |高雄安鎖 |          |  <-- 多家店共用一套系統
|  | 的資料  | | 的資料  | | 的資料  |          |      平台方是「房東」
|  | 的 LINE | | 的 LINE | | 的 LINE |          |      廠商是「房客」
|  +---------+ +---------+ +---------+          |
+===============================================+


模式 C：On-Premise / Self-Hosted（整套賣斷）
+===========+  +===========+  +===========+
| 鎖市的    |  | 台北鎖王  |  | 高雄安鎖  |  <-- 每家店買一套
| 獨立系統  |  | 獨立系統  |  | 獨立系統  |      自己 host
| 自己 host |  | 自己 host |  | 自己 host |      收授權費
+===========+  +===========+  +===========+
```

### 多租戶的定義

多租戶 = 模式 B = **一套系統服務多家客戶，資料互相隔離。**

平台營運者掌管所有合作廠商的帳號、設定、資料，但各廠商之間看不到彼此的資料。

## 2. SaaS vs 賣斷：全面比較

| 面向 | 模式 B：SaaS（多租戶） | 模式 C：賣斷 Self-Hosted |
|------|----------------------|------------------------|
| **你的角色** | 平台營運商（持續服務） | 軟體供應商（交付後放手） |
| **收入模式** | 月費/年費（MRR 遞延收入） | 一次性授權費 + 年維護費 |
| **客戶掌控度** | 你掌控一切（升級、修 bug 你決定） | 客戶掌控（自己的伺服器、自己的節奏） |
| **維護成本** | 維護一套系統 | 支援 N 個不同版本的客戶環境 |
| **LLM 成本** | 你負擔（轉嫁到月費裡） | 客戶自己的 GCP 帳號 + API key |
| **資料歸屬** | 在你的 DB 裡（你是處理者） | 在客戶自己的 DB（客戶完全擁有） |
| **客戶門檻** | 低（註冊就能用） | 高（需要 IT 團隊部署維運） |
| **典型客戶** | 中小型鎖匠店（1-20 人） | 大型連鎖/品牌原廠（有自己 IT 部門） |
| **升級體驗** | 全部客戶同時升級（你控制） | 客戶各自決定是否升級（版本碎片化） |
| **投資人估值** | 高（看 MRR，通常 10-20x ARR） | 低（看一次性收入，通常 3-5x） |
| **壁壘保護** | AI prompt/skills/harness 在你手上 | 交出去 = 送出核心壁壘 |

## 3. 賣斷的隱藏成本

即使技術上可以打包賣出，實務上會遇到：

| 問題 | 具體場景 | 成本 |
|------|---------|------|
| **版本碎片化** | 客戶 A 跑 v1.2、客戶 B 跑 v1.5、客戶 C 的 Python 版本不對 | 支援人力 x3 |
| **環境差異除錯** | 「在我的伺服器上跑不起來」—可能是 PostgreSQL 版本、GCP 憑證、防火牆 | 每個 case 2-8 小時 |
| **客戶自行修改** | 客戶改了程式碼再來報 bug | 無法重現、無法支援 |
| **安全更新** | 發現安全漏洞，要通知所有 self-hosted 客戶自行更新 | 客戶不更新 = 你的品牌風險 |
| **LLM Prompt 外洩** | 賣出去的系統包含 system.md、所有 SKILL.md、harness 邏輯 | 競爭對手可以直接抄 |

---

## 4. 短期不需要 Self-Hosted 的理由

1. **目標客戶是中小型鎖匠店** — 他們沒有 IT 部門，不會自己 host
2. **維護多版本是地獄** — 你是小團隊，無法同時支援 N 個獨立部署
3. **LLM 是核心競爭力** — prompt + skills + harness 全部交出去 = 送出壁壘
4. **SaaS 的估值比賣斷高 10 倍** — 投資人看 MRR，不看一次性授權費
5. **GitLab 的教訓** — 事後才加 self-hosted 比第一天就有痛苦得多

## 5. 市場案例

### 案例 1：ServiceTitan（家庭服務 SaaS — 最像的對標）

| 項目 | 內容 |
|------|------|
| 做什麼 | 水電工、冷氣維修、鎖匠等家庭服務業的 SaaS |
| 模式 | 純 SaaS 多租戶（不賣斷） |
| 定價 | ~$200-400/月/technician |
| 估值 | $9.5B（2024） |
| 關鍵決策 | 一開始也是小鎖匠店用，後來加大客戶。**從未提供 self-hosted**。大客戶用 dedicated instance（同一套 code，獨立部署） |
| 跟我們的差異 | 他們沒有 AI agent，主要是派工 + CRM + 計費。AI 客服是我們的差異化優勢 |

### 案例 2：Zendesk（客服 SaaS）

| 項目 | 內容 |
|------|------|
| 做什麼 | 多通道客服平台（chat、email、phone） |
| 模式 | 純 SaaS 多租戶 |
| 定價 | $19-115/agent/月 |
| 估值 | 被收購前 $10.2B |
| 關鍵決策 | 數十萬家企業共用同一套系統。**從不賣斷。** 大企業走 Enterprise 方案（獨立 pod，不是獨立部署） |
| 跟我們的類似 | 也是「AI 客服 + 工單」模式。但他們是通用型，我們是垂直型（電子鎖） |

### 案例 3：Salesforce（CRM SaaS — 經典教科書）

| 項目 | 內容 |
|------|------|
| 做什麼 | CRM + 客服 + 行銷自動化 |
| 模式 | SaaS 多租戶為主，後來推出 Salesforce Platform（PaaS） |
| 定價 | $25-300/user/月 |
| 關鍵決策 | 前 10 年純 SaaS。之後推出 Platform 讓大企業建自訂 app。**從未提供 self-hosted**（直到 Hyperforce 才做 dedicated region） |

### 案例 4：GitLab（DevOps — Hybrid 模式的代表）

| 項目 | 內容 |
|------|------|
| 做什麼 | Git + CI/CD + DevOps |
| 模式 | SaaS + Self-Hosted 並行 |
| 定價 | SaaS: $0-99/user/月；Self-Managed: $29-99/user/月 |
| 關鍵決策 | 從第一天就開源 + self-hosted。SaaS 後來才加 |
| 教訓 | Self-hosted 客戶的支援成本極高，估值長期被 GitHub 壓制。**事後才加 self-hosted = 痛苦** |

### 案例 5：91APP（台灣本土電商 SaaS）

| 項目 | 內容 |
|------|------|
| 做什麼 | 品牌電商 SaaS（開店平台 + OMO） |
| 模式 | 純 SaaS 多租戶 |
| 定價 | 月費 + 交易抽成 |
| 上市 | 2021 年台灣上櫃（6741） |
| 關鍵決策 | 不賣斷。大客戶（全聯、全家）也是 SaaS，只有客製化設定。**多租戶 + 租戶客製化 = Platform Default + Tenant Override** |

## 6. 建議的階段性策略

```
Phase 1（現在 -> 6 個月）
    模式 B：純 SaaS 多租戶
    目標客戶：中小型鎖匠店
    定價：月費制（按訊息量 or 技師數）
    不提供 self-hosted
    專注：產品打磨 + 前 10 個客戶

Phase 2（6 個月 -> 2 年）
    加入 Dedicated Instance 方案
    目標客戶：中大型連鎖鎖匠
    同一套 code，獨立 Cloud Run + 獨立 DB
    月費 3-5 倍
    專注：規模化 + 行業口碑

Phase 3（2 年+，看市場需求）
    評估是否提供 On-Premise
    只給品牌原廠或政府標案
    授權費 + 年維護費
    需要打包成 Helm Chart / Docker Compose
    前提：有足夠工程團隊（5+ 人）支援
```

## 7. 定價模型建議

### 方案結構

| 方案 | 月費 | 包含 | 超額 | 目標客戶 |
|------|------|------|------|---------|
| **Starter** | NT$ 2,000/月 | 500 則 AI 對話 + 2 技師 + 基本報表 | NT$ 3/則 | 個人鎖匠 |
| **Professional** | NT$ 6,000/月 | 2,000 則 AI 對話 + 10 技師 + 完整報表 + AI 客製 | NT$ 2/則 | 小型店面 |
| **Business** | NT$ 15,000/月 | 10,000 則 AI 對話 + 無限技師 + API 存取 + 優先支援 | NT$ 1.5/則 | 連鎖/區域 |
| **Enterprise** | 面議 | Dedicated Instance + SLA 保證 + 客製開發 | 面議 | 大型/品牌/政府 |

### 計費維度

- **AI 對話**：每次 agent.ainvoke() = 1 則（不論 tool calls 幾次）
- **技師席位**：按 active technician 數
- **儲存空間**：含 10GB 媒體儲存，超額 NT$ 5/GB
- **LINE 訊息**：平台不另外收費，但租戶需自行維持 LINE OA 訊息額度

## 8. 核心原則

1. **SaaS 先行，Self-Hosted 永遠是最後選項** — MRR 讓你活下去，賣斷的支援成本會拖死小團隊
2. **AI 能力是壁壘，不能輕易交出** — prompt + skills + harness 是核心資產，賣斷 = 送出壁壘
3. **大客戶用 Dedicated Instance，不用 Self-Hosted** — 同一套 code 獨立部署，你仍掌控更新和維護
4. **垂直 SaaS 的價值在行業 know-how** — 技術可以被複製，電子鎖維修 SOP + 品牌知識 + 故障診斷邏輯不容易被複製
