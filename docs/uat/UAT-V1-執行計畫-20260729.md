## 1. 為什麼不能照 UAT-01→09 的編號順序跑

編號是**閱讀順序**，不是執行順序。最硬的證據在 UAT-08 自己的步驟 1：

> 「建立同一技師在**兩品牌**皆可派工、且其中一筆**已接單**的情境。」

這一句同時要求三件前置：

1. **兩個已開通品牌** → UAT-09（SC-17）要跑**兩次**
2. **技師在兩品牌都被授權** → UAT-07（SC-12）的授權範圍必須覆蓋 A 與 B
3. **其中一筆已接單工單** → UAT-02（SC-05）要在第二品牌再跑到 `assigned`

照編號順序跑，會在第八支才發現前三支的產物不足，屆時要回頭重開品牌、重授權、重派工，
而重開品牌會讓已完成的 UAT-01～UAT-06 全部落在舊租戶上 —— 等於整輪重來。

其餘相依同理，多數是「上游產出的資料狀態」餵給下游：

- UAT-02 吃 UAT-01 產出的 **confirmed 問題卡**
- UAT-06 吃 UAT-01 產出的 **escalated 對話**（且必須刻意保留一則未解除接管的）
- UAT-04 的退款／取消費點測吃 UAT-02 產出的**已收款、已完工工單**
- UAT-03 的 SOP draft 由**客服回饋**觸發，空庫跑不出有意義的雙審與家族覆核

## 2. 波次排程

完整表格與逐條理由見追蹤表 ②。摘要：

| 波次 | 內容 | 相依 | 可平行 |
|---|---|---|---|
| **W0** | 22 §3 #1 migration 同步、#9 secret、#12 **金額與費率簽核** | — | 三項可平行 |
| **W1** | UAT-09 × 2（品牌 A 完整、品牌 B 至可登入＋LINE 綁定） | W0 | 兩品牌可平行 |
| **W2** | UAT-05（品牌 A）、UAT-07（授權至 A＋B） | W1 | 可平行 |
| **W3** | UAT-01（品牌 A） | W2 | 單線 |
| **W4** | UAT-02（A 完整）、UAT-02′（B 只到接單）、UAT-06 | W3 | 三者可平行 |
| **W5** | UAT-04、UAT-08 | W4 | 可平行 |
| **W6** | UAT-03 | W3、W4 | 單線（家族稽核員需預約） |
| **W7** | SC-09、SC-13（受控驗收）、UAT-10（橫切） | W5、W6 | UAT-10 可平行 |

**W0 的 #12 特別要先做。** 金額與費率若還是草稿值，UAT-02 的加價分層（≤500／501–2000／>2000）
與 UAT-04 的取消費率就是在驗假數字；費率轉正後這兩段必須整段重跑。這是排程上最容易被跳過、
代價又最大的一格。

## 3. 已知阻斷：SC-09／SC-13 不應排入本輪

`SC-09 月結與七帳本對帳` 與 `SC-13 技師跨品牌對帳與佣金請領` **目前設計上無法通過**，
原因不是尚未實作，而是三處讀寫不對齊：

- 對帳閘門查 legacy `public.settlements`
- 月結 `generate_monthly_batch` 讀寫 v2 `saas.*`
- 只有 legacy `approve_reconciliation` 會發 `commission.accrued`，v2 共簽與月結兩條寫入路徑都不發

→ 投影永遠拿不到 v2 資料，閘門一開就是每次月結永久 409（migration 118 因此刻意寫 `false`）。

**這題是 CIA gate，`CR-0189 §8` 仍待業主裁決**（v2 `co_sign_reconciliation` 要不要也走 outbox 發事件）。
未裁決前把這兩條排進正式輪次，只會卡在同一處並產出一筆假的 Fail。建議在追蹤表 ⑦ 維持
「不可簽」標記，待裁決後再排。

## 4. UAT-10 橫切受控驗收（新增一組）

130 支案例中 **34 支不隸屬任何 SC**，走查腳本天生涵蓋不到：

| 章節 | 支數 | P0 |
|---|---|---|
| 8. 權限與 RBAC（`TC-SEC-RBAC` / `TENANT` / `WEB` / `PIPE`） | 6 | 6 |
| 13. 追溯缺口收斂（`TC-AGT` / `TC-NFR` / `TC-REF`） | 14 | 9 |
| 10. 非功能（`TC-PERF` / `TC-SEC-INJ` / `TC-A11Y`） | 7 | 1 |
| 4. 工單生命週期（`TC-WO-09/10/11`） | 3 | 2 |
| 12. Web 與顯示整合 | 2 | 1 |
| 9.1 系統例外 | 2 | 1 |
| **合計** | **34** | **20** |

它們是橫切關注點（權限邊界、跨租戶隔離、注入、稽核鏈、隱私、效能、可及性），
本質上不是「某個角色走一遍」能驗的 —— 這正是它們沒有 SC 的原因，不是遺漏。

但**九支走查全綠 ≠ 全部驗完**。特別是 `TC-SEC-RBAC-02/04/05`、`TC-SEC-TENANT-01`、
`TC-SEC-WEB-01`、`TC-SEC-PIPE-01` 六支全為 P0，而 22 §3 第 6 類明寫 RBAC「**未達即不得上線**」。
故另立 UAT-10，於 W7 由 Release Manager 執行、業主簽核。

## 5. 回歸範圍

某支腳本判 Fail 時，**修完只重跑自己是不夠的** —— 下游是拿修復前產生的資料驗收的。
完整矩陣見追蹤表 ⑤，最重的三條：

| Fail 的腳本 | 必須連帶重跑 |
|---|---|
| UAT-09 | 全部（沒有可用租戶） |
| UAT-07 | UAT-02、UAT-02′、UAT-08 |
| UAT-01 | UAT-02、UAT-06、UAT-03 |

另一條容易漏：**UAT-03 Fail 或 SOP 內容變更後，要回頭重測 UAT-01 的知識類回答** ——
SOP 發布會改變 agent 行為，這是唯一一條「下游影響上游」的邊。
