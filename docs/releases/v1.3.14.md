## 變更摘要 (WHAT)

新增 4 份品牌通用文件，延續 v1.3.13 的 `{Brand}/_brand.md` 機制：

| 檔案 | 內容 |
|---|---|
| `Chatlock/_brand.md` | 系列概述（A90 / AI-88 / AI-99）、APP 名稱「chatlock AI99」、2.4G Wi-Fi 限制、通用配對流程、跨型號設計重點（拆螢幕＝斷網、Type-C 緊急供電） |
| `3E/_brand.md` | 系列概述（F(T7) / TX）、APP / Wi-Fi 通用設定、Type-C 緊急供電、受口盒對位通用診斷、F(T7) 安裝方向（直立 / 橫式） |
| `Philips/_brand.md` | 資料缺乏聲明 + 通用故障引導 + 派工建議；明確禁止 LLM 編造按鍵 SOP |
| `Milre/_brand.md` | 資料缺乏聲明 + 通用故障引導 + 派工建議；明確禁止 LLM 編造按鍵 SOP |

## 背景與動機 (WHY)

v1.3.13 在 Dormakaba 完成 `_brand.md` PoC 後，效果符合預期。本次將機制擴展到其他有實質內容（Chatlock / 3E）或仍需品牌入口聲明（Philips / Milre）的品牌，讓「客戶已知品牌但型號未確認」情境下都能取得品牌共通知識，而不是退回到跨品牌 `_common/*` 的模糊回答。

對 Philips / Milre 這類 bronze 資料缺乏的品牌，`_brand.md` 的價值是**集中放置「資料缺乏聲明 + 派工建議」**，避免 LLM 在型號未知時隨意搬運其他品牌的步驟或編造 SOP。

## 影響評估 (IMPACT)

- 破壞性變更：無。純內容新增，loader 機制已於 v1.3.13 完成。
- 內容來源：全部從既有 mega-doc 萃取（路線 A），符合 `bronze-only` 規則，未引用任何 PDF。
- 行為變更（部署後）：
  - 「Chatlock 怎麼配對 APP」（不知型號）→ AI 載入 `Chatlock/_brand`，給出通用配對流程與 APP 名稱。
  - 「3E 一關門就嗶嗶」（不知型號）→ AI 載入 `3E/_brand`，引用「受口盒對位」跨型號通用診斷。
  - 「Philips 怎麼設定指紋」（不知型號）→ AI 載入 `Philips/_brand`，依資料缺乏聲明告知無法給按鍵步驟、安排派工，不再編造。
- 未做的品牌：AiLock（單型號品牌，`{Brand}/{Model}` 即品牌通用）；Kaadas（已有 stub 文件，避免重複資料缺乏聲明）。loader 對未建 `_brand` 的品牌會安全降級到 `_common/*`。
- 後續動作：需 `./agent/scripts/deploy.sh` 重新 build + deploy。
