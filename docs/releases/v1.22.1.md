- **版本**: v1.22.1（前版：v1.22.0 → 本版升級類型：PATCH）
- **Commit**: `dfd2778` (2026-05-06 07:23)
- **分支**: feat/api-subflow-endpoints

- **影響模組**: agent/memory（連帶解除 harness/debounce 與 harness/memory_manager 的同源失敗）

## 變更摘要 (WHAT)

- `agent/memory/postgres_saver.py` 改用 `psycopg_pool.AsyncConnectionPool`，由 pool 在 checkout 時驗證連線並回收壞掉的連線
- 保留原本 `autocommit=True, prepare_threshold=0, row_factory=dict_row` 的連線參數，介面不變，呼叫面（`app.py`、`scripts/view_context.py`）零修改
- 新增可調整參數：`pool_max_size`（預設 10）、`pool_max_idle_seconds`（預設 240，小於 CloudSQL ~600s idle 上限）、`pool_checkout_timeout`（預設 30）

## 背景與動機 (WHY)

生產環境 Cloud Run logs 顯示 LINE 用戶送訊息後，agent 連續拋 `psycopg.OperationalError: the connection is closed`，所有對話只能收到「系統大腦剛剛稍微當機了一下」的兜底回覆。同個錯誤同時出現在三條呼叫路徑：

1. `harness/debounce.py:247` — 清理殘留多模態
2. `agent.aget_state` / `aput`（agent 主流程）
3. `harness/memory_manager.py:88` — `maybe_compress` 背景任務

根因：`postgres_saver.py` 在啟動時建立**單一** `AsyncConnection` 並重用整個 process 生命週期。CloudSQL 對 idle 連線約 600 秒會主動關閉，連線一旦死亡，LangGraph 的 `AsyncPostgresSaver` 沒有任何重連邏輯，整個 checkpointer 直接報廢。CLAUDE.md 提及的 4 個 DB 模組 `_ensure_conn()` 重連模式並未涵蓋 checkpointer，這個模組是漏網之魚。

選擇 pool 而非手寫 `_ensure_conn()` 的原因：`AsyncPostgresSaver` 原生支援 `AsyncConnection | AsyncConnectionPool`（見 `langgraph.checkpoint.postgres._ainternal.Conn`），用 pool 不需要 wrap saver、也不會在重連視窗丟掉並發請求。

## 影響評估 (IMPACT)

- 破壞性變更：無。`build_postgres_saver` / `close_postgres_conn` 介面不變
- 後續動作：無 schema 異動，部署 Cloud Run 即可生效。不需要 migration
- 依賴：`psycopg-pool` 已是 `langgraph-checkpoint-postgres` 的傳遞依賴，不需動 `requirements.txt`

## 驗證方式

- 模組匯入：`cd agent && python -c "from memory.postgres_saver import build_postgres_saver, close_postgres_conn; print('ok')"` 通過
- API 相容性：核對 `AsyncConnectionPool.__init__` 簽名、`AsyncPostgresSaver` 接受 pool 路徑（`get_connection` 對 pool 走 `async with conn.connection()` 取臨時 conn）
- 待人工驗證：部署後在 LINE 連續發訊息，等 ≥ 10 分鐘 idle 後再發一則，確認 checkpointer 不再報「the connection is closed」
