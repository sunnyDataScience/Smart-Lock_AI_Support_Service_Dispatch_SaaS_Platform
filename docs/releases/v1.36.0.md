## 變更摘要 (WHAT)

- 新增 `agent/harness/reschedule_flex.py`：`build_reschedule_flex()` 產生 LINE Flex bubble JSON（header + 1-3 個 postback 時段按鈕 + 「都不方便」拒絕按鈕 + footer），`parse_postback_data()` 解析 `reschedule_select?wo=...&start=...&end=...` 格式
- `agent/app.py` 新增 `PostbackEvent` 處理：webhook 收到 postback 後透過 httpx 內部呼叫 api，使用 `INTERNAL_API_BASE_URL`/`INTERNAL_API_TENANT_ID`/`INTERNAL_API_BEARER` 三個環境變數
- `api/services/work_order_service.py` 新增 `confirm_reschedule_by_customer`（UPDATE wo.scheduled_at + work_order_events + WS publish）與 `reject_reschedule_by_customer`（event + WS）
- `api/routers/work_orders.py` 新增兩個 REST endpoints：`POST /work-orders/{id}/reschedule/customer-confirm`（operationId=confirmCustomerReschedule）與 `.../customer-reject`（rejectCustomerReschedule）
- OpenAPI spec 同步、TS types 重新生成；總 endpoints 125 → 127

## 背景與動機 (WHY)

Flow 11（客戶不在場）原停在 75%：技師端 v1.7.0 已可送 1-3 個 proposed_slots，但「客戶看到 Flex 並能直接點選回寫工單」這一段一直缺。導致實際營運只能用口頭協調或重派工單，破壞 SLA 計時。F2 需打通跨 service 鏈路：agent → LINE Flex push → 客戶 postback → agent webhook → api 內部呼叫 → wo update + WS 推回技師。

## 影響評估 (IMPACT)

- 破壞性變更：無；既有 `proposeReschedule` 行為不變
- 新增環境變數需求（部署）：`INTERNAL_API_BASE_URL`、`INTERNAL_API_TENANT_ID`、`INTERNAL_API_BEARER`，agent service 需配置才能呼叫 api 內部端點
- Flow 11 完成度：75% → 100%；系統總體：97% → 98%
