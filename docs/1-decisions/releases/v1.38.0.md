## 背景與動機 (WHY)

Phase 1 還原系列（PR #17–#22）完成後架構單一、deps 就位。Phase 2 觸發條件雖標需 V1 上線 + E2E ≥ 80%，但其中 RP2.2 / 2.3 / 2.6 是**獨立、低風險**的解耦/收斂，與 RP2.1 debounce 拆分無依賴關係。**先做這 3 個可降低 RP2.1 的前置障礙**：

- RP2.2 / 2.3 解除反向耦合 → pydeps 圖乾淨 → 拆 debounce.py 時不會被 cycle 卡住
- RP2.6 narrow exception → 拆分時的 typo / 錯誤 import 會直接拋出，不被 `except Exception` 吞掉

採 worktree 並行處理而非單一 branch 序列做：3 個任務無共享檔案衝突（RP2.2 動 `core/brand_match.py` + `skills/tools.py`、RP2.3 動 `app.py` + `debounce.py` 簽章、RP2.6 動 except 子句），可獨立 commit / push / PR / merge，總時 < 序列模式 1/3。

## 影響評估 (IMPACT)

- ✅ **pydeps 圖**：skills 不再指回 harness、harness 不再指回 agent — 兩條反向 cycle 全消失
- ✅ **lint**：pylint/ruff BLE001 規則開啟後可乾淨通過（除已標 `# noqa: BLE001` 的故意放行）
- ✅ **debug 體驗**：typo / programming bug 不再被 `except Exception` 吞掉，dev 期間直接拋出
- ✅ **production safety net**：DB / LLM / I/O 仍走 graceful 路徑（型別組合涵蓋常見 transient errors）
- ✅ **行為等價**：純 import path 重組 + 狀態 ownership 遷移 + except 子句 narrow，無業務邏輯變更
- ⚠️ **下次 sync 後注意**：`debounce.init()` 簽章多了 `system_prompt_getter` kwarg，呼叫端 `app.py` 已同步；外部呼叫者（測試 / 第三方）需更新
