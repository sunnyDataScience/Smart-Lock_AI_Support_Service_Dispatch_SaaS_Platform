## 執行摘要

現有系統設計約涵蓋 **45% 的總需求**。V1.0 AI 客服核心架構尚稱完整，但存在以下 **重大盲區**：

1. **異常／例外流程** — 系統僅設計了「正常路徑」，幾乎完全忽略出錯時的處理（客訴、爭議、改派、退款、超出範圍工作、延遲）
2. **多代理人架構** — 合約 M5 里程碑明確要求，但設計幾乎為零
3. **人機協作流程** — 合約要求高情緒、高金額、安全相關案件必須有人工介入，但無任何詳細流程設計
4. **使用者角色模型** — 現有設計僅 3 個角色（消費者、技師、管理員），但實際業務至少需要 5-6 個角色（終端客戶、社區/建商、品牌原廠、經銷商/維修中心、管理員、師傅）
5. **Token／成本控制** — 合約明確要求但設計完全缺失
6. **CRM 與售後服務流程** — 無客戶關係管理、滿意度追蹤或保固追蹤機制

### 1.2 工單缺口 — 關鍵流程缺失

**您的筆記：**

> 師傅延遲通知；案件超出原始範圍，繼續還是改期；「ProblemCard 寫得蠻清楚的，大概知道要帶什麼工具。」「到了現場看情況比描述的複雜。」導致改期和缺料；師傅確認案件所需材料/工具/配件；內部配件材料請購；案件+材料資料庫；注意客戶原始門損壞狀況及外觀變更通知

**系統設計現況：** 工單有 5 階段生命週期（created→assigned→in_progress→completed→cancelled），但各階段內 **無任何異常處理機制**。

**必須補充：**


| 缺失項目            | 說明                                                    | 優先級 |
| --------------- | ----------------------------------------------------- | --- |
| **延遲通知流程**      | 師傅通報延遲 → 客戶收到新預計到達時間 → 嚴重延遲時管理員收到警報                   | P0  |
| **案件範圍變更／改期流程** | 現場發現與 ProblemCard 不符 → 師傅回報範圍變更 → 重新報價 → 客戶核准 → 改期或繼續 | P0  |
| **材料／工具確認步驟**   | 派工前：師傅審查 ProblemCard 並確認所需材料/工具/配件；需要特殊工具時標記提醒        | P0  |
| **內部材料請購**      | 向庫存申請配件/材料 → 追蹤消耗 → 退還多餘 → 外購選項                       | P1  |
| **案件＋材料對照資料庫**  | 每種案件類型對應：所需材料清單、特殊工具、常用配件                             | P1  |
| **門外觀變更通知**     | 維修將改變門外觀或原始功能 → 開工前客戶書面確認                             | P0  |
| **缺料處理流程**      | 師傅到場但沒有正確零件 → 部分完工 → 改期 → 客戶溝通                        | P0  |

### 1.4 使用者角色模型 — 過於狹窄

**您的筆記：**

> 應該有原廠的介面？使用者定義：終端客戶、師傅、派工中心管理面板和品牌原廠？面板應包含經銷商/維修中心、管理員、師傅、客戶
> 使用者應為：客戶（終端用戶、社區、建商）、管理者（原廠、維修、派工承包商）、admin（可同時為師傅和管理員）

**系統設計現況：** 僅 3 個使用者角色：消費者（LINE）、技師（Web App）、管理員（Panel）。RBAC 有 4 個角色：line_user、technician、reviewer、admin。

**必須補充：**


| 缺失角色          | 存取權限              | 使用情境                          | 優先級 |
| ------------- | ----------------- | ----------------------------- | --- |
| **品牌原廠**      | 唯讀儀表板＋產品資料管理 API  | 查看其品牌故障統計、更新產品手冊、管理保固規則       | P1  |
| **社區／建商**     | 批次服務請求入口＋稽核紀錄     | 提交多戶維修需求、查看完工證據、保固追蹤          | P1  |
| **經銷商／維修中心**  | 區域派工子管理面板         | 管理所屬區域師傅、處理區域定價、區域報表          | P2  |
| **專家資料庫 API** | 開放 API 供品牌商/製造商使用 | 上傳價目表、產品服務資訊、新型號規格 — 關鍵數據累積策略 | P1  |


**您的關鍵洞察：**

> 「既然資料很難收集，我們應該開放一個好的專家資料 DB API 讓他們上傳價格和產品服務資訊，這非常關鍵，我們開始累積數據，有一天他們必須自己上傳和更新。」

這是一個 **戰略性數據獲取通道**，所有設計文件中均未提及。必須設計為品牌製造商的自助入口/API。

### 1.6 圖片／影像處理 — 需要釐清

**您的筆記：**

> 圖片傳送：使用者傳送電子鎖故障照片、錯誤代碼螢幕截圖，AI 需要進行 Vision 分析？我們真的能從照片驗證問題嗎？

**合約現況：** V21 SOW 明確排除「AI 圖片辨識」— 照片僅作為附件。
**投資人規格書：** 將「AI 圖片辨識」列為範圍外。

**但您的護城河分析提問：** 「照片特徵 → 故障分類 → 是否需到場的判斷邏輯，現在能做 Picture vs ProblemCard 嗎？」

**討論建議：**

- 目前範圍：照片儲存為附件，不進行 AI 視覺分析
- 未來潛力：Vision API 可辨識螢幕截圖上的錯誤代碼、從照片識別鎖具型號
- **需要決策：** 是否透過變更請求將 Vision 納入範圍？需進行成本效益分析

### 1.13 授權／權限資料庫

**您的筆記：** 「我看不到多使用者、授權設定資料庫」

**系統設計現況：** 安全架構圖中提到 RBAC（4 個角色），但：
