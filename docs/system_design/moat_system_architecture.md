# Tier 1 護城河系統架構 (Moat System Architecture)

**版本**: v1.0
**日期**: 2026-03-31
**對應合約**: SPA-Funngo-001 V21
**定位**: 本文件為技術策略文件，定義平台十大護城河的系統性架構、數據飛輪機制及防禦層級。

> **SOW 邊界聲明**: 標記為 `[SOW]` 之功能為合約必交付項目；標記為 `[MOAT]` 之功能為護城河增值功能，需經變更請求流程（合約 11.2 條）或以獨立產品路線圖管理。護城河功能不對應股份解鎖條件。

## 里程碑定義 (Milestone Definition)

本文件中 **M1 / M2 / M3** 為專案三大里程碑，對應合約交付階段與護城河數據累積時程：


| 代號     | 時間範圍              | 定位      | 重點                             |
| ------ | ----------------- | ------- | ------------------------------ |
| **M1** | W1–W17（約 0–4 個月）  | 種子數據收集  | AI 客服上線、知識庫運作、ProblemCard 開始累積 |
| **M2** | W18–W31（約 4–8 個月） | 定價與營運數據 | 派工系統、定價引擎、完工回報、會計結算            |
| **M3** | 5 個月（約 8–13 個月）   | 智慧層     | 影子驗證、報價信心分數、預測備料、語言模型 v2       |


### 護城河表格中 M1/M2/M3 欄位標記說明


| 標記                   | 意思             |
| -------------------- | -------------- |
| `Seed`               | 播種階段，載入初始數據    |
| `Build`              | 正式建構功能         |
| `V1` / `V2`          | 功能版本迭代         |
| `Basic` / `Advanced` | 從基礎到進階         |
| `Skeleton` / `Full`  | 骨架先行，後續補齊完整功能  |
| `Schema`             | 先定義資料結構，功能稍後實作 |
| `SOW`                | 該里程碑的合約必交付項目   |
| `-`                  | 該階段不涉及此護城河     |


> **核心邏輯**: M1 先讓數據開始流動 → M2 建構營運骨幹 → M3 啟動智慧層讓數據產生複利效果。到 M3 運作 12 個月後，切換成本達到「實質不可逆」。

## 二、飛輪架構 (Flywheel Architecture)

平台以 **ProblemCard** 為通用數據交換格式，三個飛輪互鎖：

```
═══════════════════════════════════════════════════════════════
                    飛輪 1: 知識飛輪
        每一次成功解決都讓 AI 更聰明
═══════════════════════════════════════════════════════════════

  消費者口語描述 ──→ [A 產業語言模型] ──→ 標準化分類
                                              │
                                              v
                                      ┌──────────────┐
                                      │ ProblemCard  │
                                      │  (通用 Hub)   │
                                      └──────┬───────┘
                                             │
                        ┌────────────────────┼────────────────────┐
                        v                    v                    v
                 [I 硬體診斷]         [三層解決引擎]         [情緒分流]
                 故障碼→根因           L1→L2→L3              [SOW]
                        │                    │
                        v                    v
                 診斷精度提升 ←──── [F 數據飛輪] ←──── SOP 自動生成
                                      │
                                      v
                               影子驗證 + 失敗解剖
                                      │
                                      v
                              知識庫品質持續提升
                                      │
                                      └──→ L1 命中率提升 ──→ 更多自動解決

═══════════════════════════════════════════════════════════════
                    飛輪 2: 定價飛輪
        每一筆完工都讓報價更精準
═══════════════════════════════════════════════════════════════

  ProblemCard ──→ [C 定價引擎] ──→ 系統報價
                                      │
                                      v
                              師傅完工回報
                                      │
                        ┌─────────────┼─────────────┐
                        v             v             v
                 [D 完工證據]   [B 報價智慧]   [E 會計結算]
                 GPS+照片+時間   偏差分析+信心   傳票+對帳
                        │             │
                        v             v
                 品質證據庫     報價精準度提升
                                      │
                                      v
                              成交率提升 → 更多完工 → 更多數據

═══════════════════════════════════════════════════════════════
                    飛輪 3: 營運飛輪
        每一次派工都讓調度更智慧
═══════════════════════════════════════════════════════════════

  ProblemCard ──→ [G 演算法派工] ──→ 最適師傅
                       │                    │
                       v                    v
                實際車程回報           [H 預測性備料]
                       │             攜帶正確零件
                       v                    │
                車程預測優化                  v
                       │             一次修好率提升
                       v                    │
                [J 危機工作流]               v
                Red_Code 應急          師傅信任度提升
                       │                    │
                       v                    v
                應急經驗累積 ──→ 更好的派工決策 ──→ 更多完工數據
```

### 飛輪交叉強化

知識飛輪產出的 ProblemCard 完整率提升 → 定價飛輪的報價精準度提升（更完整的故障描述 = 更準的估價）→ 營運飛輪的派工精準度提升（更準的 ProblemCard = 更好的師傅匹配）。

## 三、數據引力圖 (Data Gravity Map)

每個護城河產出專屬數據，被其他護城河消費。連線越多 = 越難複製。


| 護城河           | 產出的專屬數據                  | 被誰消費                 | 引力分數  |
| ------------- | ------------------------ | -------------------- | ----- |
| **A** 產業語言模型  | 術語映射表、口語字典、錯字庫、故障分類樹     | ProblemCard, 三層引擎, I | 4     |
| **B** 報價智慧引擎  | 報價偏差紀錄、信心分數、地區彈性模型、成交率   | C, G, J              | **7** |
| **C** 標準化定價引擎 | 規則版本、加價應用紀錄、報價接受/拒絕紀錄    | B, E                 | 3     |
| **D** 完工證據標準  | GPS 標記照片庫、完工時間基準、品質語料    | F, B, J              | 4     |
| **E** 會計金流結算  | 交易帳本、師傅收入模式、爭議紀錄         | B, J                 | 4     |
| **F** 數據飛輪    | 影子驗證語料、失敗解剖紀錄、SOP 效能分數   | A, 三層引擎, I           | **6** |
| **G** 演算法派工   | 實際車程矩陣、師傅績效剖面、路徑優化歷史     | H, J, B              | **7** |
| **H** 預測性備料   | 零件使用頻率模型、車載庫存快照、缺件紀錄     | G, C                 | 3     |
| **I** 硬體診斷映射  | 故障碼→根因映射、蜂鳴/燈號辭典、診斷決策樹   | ProblemCard, 三層引擎, F | 4     |
| **J** 危機工作流   | Red_Code 事件庫、重複投訴模式、仲裁結果 | F, G                 | **6** |


**基石護城河三角 (Keystone Triangle)**:

```
        F 數據飛輪
       /          \
      /    核心    \
     /    三角    \
    A 產業語言 ── B 報價智慧
```

移除三角中任一個 → 系統性崩潰：

- 移除 **F**: 知識庫變成靜態 CRUD，AI 不再進步
- 移除 **B**: 報價變成死規則，成交率下降，師傅流失
- 移除 **A**: ProblemCard 完整率從 85% 跌到 50%，L1 命中率崩盤

## 八、競爭者殲滅區 (Kill Zone)

一個資金充裕的競爭者面對的累加障礙：


| 障礙          | 說明                                                             | 追趕時間     |
| ----------- | -------------------------------------------------------------- | -------- |
| **冷啟動問題**   | 需 5,000+ 真實 ProblemCards + 解決數據來訓練語言模型和校準報價                    | 12-18 月  |
| **術語壁壘**    | 產業語言模型含數千個口語映射（如「嗶嗶叫的東西壞了」→ `keypad_beeping_error`），來自真實對話而非手冊 | 無捷徑      |
| **定價悖論**    | 無歷史報價偏差數據 → 報價不準 → 客戶或師傅流失 → 無法累積數據。雞生蛋問題。                     | 18-24 月  |
| **師傅網路鎖定**  | 師傅有績效檔案、派工歷史、收入模式 → 換平台 = 從零聲譽開始                               | 不可逆      |
| **跨護城河依賴網** | 即使完美複製單一護城河，缺少其他護城河的數據依賴 = 降級版本                                | 全棧 24 月+ |
| **在地化護城河**  | 完工證據標準 + 會計傳票格式校準台灣 GAAP；危機工作流校準消保法                            | 6-12 月   |


**結論**: Layer 3 功能可在 3-6 月複製。Layer 2 結構可在 6-9 月建置。但 Layer 0-1 需要 **18-24 月的真實營運數據** — 且這段期間我方數據優勢持續複利增長。

## 十、ProblemCard 作為通用數據 Hub

合約定義十要求的最低欄位 + 護城河預留欄位：

```json
{
  // === 合約必要欄位 (SOW) ===
  "customer_id": "U1234567890abcdef1234567890abcdef",
  "location": {"address": "新北市板橋區...", "gps": [25.0145, 121.4593]},
  "brand_model": {"brand": "Samsung", "model": "SHP-DP609"},
  "fault_description": "指紋辨識失敗率突然升高",
  "attachment_links": [{"url": "...", "photo_type": "handle_front"}],
  "sentiment_label": "neutral",
  "preliminary_diagnostic_logic": "可能為指紋模組髒污或軟體異常",

  // === 護城河預留欄位 (M1 可為 null) ===
  "fault_category": "fingerprint_module_failure",     // Moat A: 標準分類
  "emotion_severity": 2,                              // Moat J: 1-5 級
  "is_urgent": false,                                 // Moat J: 急件標記
  "predicted_parts": ["fingerprint_sensor_DP609"],     // Moat H: 備料預測
  "device_error_log": null,                            // Moat I: IoT 預留
  "crisis_code": "Normal",                             // Moat J: Red_Code/Warning/Normal
  "door_status": {"material": "木門", "thickness": "4cm", "direction": "左開"},
  "network_status": "wifi_connected",
  "symptoms": ["指紋辨識失敗", "偶爾可以", "清潔後仍然"],
  "completeness_score": 0.90
}
```

> 預留欄位在 M1 為 null 值，但 Schema 必須存在。這不增加開發成本但保留擴展性。合約定義十說「至少包含」而非「僅包含」，允許額外欄位。
