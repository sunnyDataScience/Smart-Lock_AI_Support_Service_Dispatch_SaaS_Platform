### 0.1 領域知識盤點

**對口窗口：** 甲方資深技師
**截止日期：** Phase 0 啟動前（W1）

📂 `requirements/01_domain_knowledge/`

| 子項 | 交付物 | 格式 | 說明 |
|:-----|:-------|:-----|:-----|
| 0.1.1 | 產品目錄 | Excel/CSV | 所有服務品牌（Samsung, Yale, Gateman, 耶魯, 加安...）、每品牌的型號清單、每型號的常見故障類型、電池型號、適用鎖型（密碼鎖/指紋鎖/電子把手/推拉鎖） |
| 0.1.2 | 客戶分群 | 文件 | 目前實際的客戶分類方式：住宅用戶、商辦用戶、社區大樓管委會、建設公司等，每類的典型需求與報修頻率 |
| 0.1.3 | 業務術語表 | 文件 | 內部術語的正式定義（如「鎖舌」「天地鉤」「電路板」「把手座」「面板」「門扇厚度」「門框間距」「電子模組」等） |
| 0.1.4 | 現行客服與派工流程 | 文件/影片 | 目前從消費者 LINE 報修到技師到場到結案的完整流程紀錄，包含目前的 LINE 群組溝通方式、紙本記錄、Excel 記帳等 |

**為什麼需要：** 開發團隊不懂電子鎖行業。如果不給這些，ProblemCard 的欄位設計會對不上現實，AI 問診對話會問出外行問題，消費者會覺得這個系統不專業。

**允收標準：**
- 產品目錄涵蓋至少 5 個品牌、每品牌至少 3 個主力型號
- 故障類型涵蓋至少 20 種常見故障
- 術語表至少包含 30 個專業術語
- 現行流程以文字 + 截圖或影片形式記錄，覆蓋從報修到結案的完整環節

### 0.2 知識庫種子資料

**對口窗口：** 甲方 + PM
**截止日期：** Phase 1 W3

📂 `requirements/02_knowledge_base_seed_data/`

| 子項 | 交付物 | 格式 | 說明 |
|:-----|:-------|:-----|:-----|
| 0.2.1 | 歷史維修案例 | Excel/CSV | 至少 200 筆結構化的歷史維修案例，每筆包含：品牌、型號、故障描述、解決步驟、是否需要到場、使用材料、耗時。這些案例將作為向量搜尋的 L1 種子資料。 |
| 0.2.2 | 產品操作手冊 | PDF | 所有服務品牌的產品操作手冊 PDF 檔案。系統將自動進行 PDF 切分（Chunking）、向量化，作為 RAG L2 層的知識來源。 |
| 0.2.3 | FAQ 種子資料 | Excel/CSV | 至少 50 條常見問答，涵蓋：電池更換、密碼重設、WiFi 設定、指紋登錄、門鎖異響、無法上鎖等高頻問題。 |
| 0.2.4 | 案例品質標注規範 | 文件 | 定義案例結構化的標準：哪些欄位必填、品質要求、分類規則，確保匯入的案例品質一致。 |

**為什麼需要：** AI 客服的準確率直接取決於知識庫的品質與數量。案例庫是 L1 向量搜尋的基礎，產品手冊是 L2 RAG 的基礎。沒有種子資料，AI 上線就是「空殼」。合約要求 AI 準確率 >= 80%（50 題測試），沒有足夠的種子資料根本達不到。

**允收標準：**
- 歷史案例 >= 200 筆，且至少涵蓋 5 個品牌
- 每筆案例的「故障描述」和「解決步驟」欄位均不為空
- 產品手冊 PDF 清晰可辨識（非掃描模糊圖檔），至少涵蓋主力品牌
- FAQ >= 50 條，涵蓋至少 10 種問題類別

### 0.3 AI Prompt 設計

**對口窗口：** Tech Lead
**截止日期：** Phase 1 W2

📂 `requirements/03_resolution_rules/`

| 子項 | 交付物 | 格式 | 說明 |
|:-----|:-------|:-----|:-----|
| 0.3.1 | 意圖識別 Prompt | Markdown/JSON | 用於分類用戶訊息意圖（`repair` / `purchase` / `inquiry` / `dispatch` / `complaint` / `other`）的 System Prompt 與 Few-shot 範例 |
| 0.3.2 | ProblemCard 擷取 Prompt | Markdown/JSON | 用於從對話上下文中提取結構化欄位（brand, model, symptom, location, door_type, network_type, urgency）的 Prompt 模板，含 Pydantic Schema 約束 |
| 0.3.3 | RAG 回覆生成 Prompt | Markdown/JSON | 用於整合檢索到的手冊 chunks 並生成步驟化解決方案的 Prompt，需包含來源標注指示（「根據 XX 手冊第 X 頁」）和幻覺抑制策略 |
| 0.3.4 | SOP 草稿生成 Prompt | Markdown/JSON | 用於從已成功解決的對話中自動提取 SOP 草稿（問題描述、適用條件、解決步驟、注意事項）的 Prompt 模板 |

**為什麼需要：** Prompt 是 AI 系統的「靈魂」。意圖識別 Prompt 決定用戶的問題能不能被正確分類，ProblemCard 擷取 Prompt 決定問題卡的完整度（合約要求 >= 85%），RAG Prompt 決定 AI 回覆的品質，SOP Prompt 決定知識庫自演化的品質。

**允收標準：**
- 每個 Prompt 包含明確的 System Prompt + 至少 3 個 Few-shot 範例
- ProblemCard 擷取 Prompt 在 10 筆測試案例上的欄位擷取準確率 >= 80%
- RAG Prompt 的回覆包含來源標注且無明顯幻覺
- SOP Prompt 生成的草稿結構完整（4 大區塊皆有內容）

### 0.4 LINE Bot 設定

**對口窗口：** IT / PM
**截止日期：** Phase 0（W1）

📂 `requirements/04_problem_diagnosis_patterns/`

| 子項 | 交付物 | 格式 | 說明 |
|:-----|:-------|:-----|:-----|
| 0.4.1 | LINE Official Account | 帳號資訊 | 品牌 LINE 官方帳號（已開通認證帳號），包含 Channel ID、Channel Name |
| 0.4.2 | Messaging API Channel | 設定文件 | LINE Developers Console 中已建立 Messaging API Channel，提供 Channel Secret 與 Channel Access Token（Long-lived） |
| 0.4.3 | Webhook URL | 設定確認 | 確認 Webhook URL 設定方式與測試環境的 URL（開發階段可使用 ngrok），正式環境需 HTTPS |
| 0.4.4 | Rich Menu 設計稿 | 圖片 + JSON | Rich Menu 的視覺設計稿（甲方提供品牌視覺），包含按鈕區域定義：「報修諮詢」「查詢進度」「常見問題」「聯繫客服」等 |

**為什麼需要：** LINE Bot 是消費者與平台互動的唯一入口。沒有 LINE OA 和 Messaging API Channel，整個 V1.0 的開發無法啟動。Rich Menu 是消費者第一眼看到的介面，直接影響使用體驗。

**允收標準：**
- LINE OA 為認證帳號（灰盾或藍盾），已啟用 Messaging API
- Channel Secret 與 Channel Access Token 可成功呼叫 LINE API
- Webhook URL 可接收測試訊息（HTTP 200 回應）
- Rich Menu 設計稿包含至少 4 個功能按鈕，符合品牌視覺規範

|:-----|:-------|:-----|:-----|
| 0.5.1 | 技師名冊與技能清單 | Excel/CSV | 所有簽約技師的基本資料：姓名、聯絡電話、品牌技能認證（多選，如 Samsung 認證、Yale 認證）、認證到期日、鎖型專長（密碼鎖/指紋鎖/推拉鎖等） |
| 0.5.2 | 服務區域對照表 | Excel/CSV | 每位技師的服務區域：以行政區為單位（如：台北市信義區、新北市板橋區），每位技師可設定多個服務區域 |
| 0.5.3 | 技師可用時段表 | Excel/CSV | 每位技師的預設可接單時段：週一至週日的可用時間區間，以及特殊不可用日期 |

**為什麼需要：** 派工引擎的核心邏輯是「技能 x 地區 x 評分 x 可用時段」的匹配演算法。沒有技師的技能與區域資料，派工引擎就是一台沒有燃料的引擎。

**允收標準：**
- 技師名冊至少 10 位技師
- 每位技師至少標注 1 個品牌技能認證
- 每位技師至少設定 1 個服務區域
- 可用時段表涵蓋所有技師的預設排班

### 0.6 計價規則定義

**對口窗口：** 甲方 + PM
**截止日期：** Phase 5 W19

📂 `requirements/06_line_bot_templates/`

| 子項 | 交付物 | 格式 | 說明 |
|:-----|:-------|:-----|:-----|
| 0.6.1 | 標準報價矩陣 | Excel/CSV | 品牌 x 鎖型 x 工項 的三維報價表。每個組合定義：基礎工資、標準材料費、總價。例如：Samsung DP960 指紋鎖 / 更換面板 / 工資 $800 + 材料 $2500 = $3300 |
| 0.6.2 | 特殊加價規則 | Excel | 所有加價項目的定義：夜間加價（22:00-06:00, +30%）、假日加價（國定假日/週日, +50%）、遠程加價（距離 > 30km, +$500 固定）、高樓加價（> 5F 無電梯, +$200/層）等。每條規則包含：觸發條件、加價方式（固定金額/百分比）、是否可疊加 |
| 0.6.3 | 結算與墊款規則 | 文件 | 定義技師墊付款的申請流程、審核標準、月結結算週期、結算憑證格式需求（是否需要符合特定會計軟體匯入格式） |

**為什麼需要：** 報價引擎是消費者「要不要派工」的關鍵決策依據。報價不透明或不一致，消費者不會接受派工。結算規則不清楚，技師不會信任平台。

**允收標準：**
- 報價矩陣至少涵蓋 5 個品牌 x 3 種鎖型 x 5 種工項 = 75 個組合
- 每個組合的工資與材料費分開列示
- 至少定義 3 條特殊加價規則
- 結算規則文件經甲方與技師代表共同確認

### 0.8 營運指標基線

**對口窗口：** 甲方營運
**截止日期：** Phase 1

📂 `requirements/08_business_metrics/`

| 子項 | 交付物 | 格式 | 說明 |
|:-----|:-------|:-----|:-----|
| 0.8.1 | 現行轉化率基準 | Excel | 目前的實際營運數據：每月報修量、自助解決率（目前可能為 0%）、平均處理時間（從報修到結案）、人工客服回覆量、每月派工量、技師平均完工時間。有多少就給多少，沒有也要明確標注「目前無此數據」 |
| 0.8.2 | 目標 KPI | Excel | 導入系統後的目標值：AI 準確率 >= 80%、自助解決率 >= 60%（上線 3 個月後）、AI 首次回應 < 5 秒、同時在線 >= 50 人（V1.0）/ >= 100 人（V2.0） |
| 0.8.3 | 告警閾值 | Excel | 什麼數字算「異常」需要告警：如 AI 準確率連續 3 天低於 70%、自助解決率低於 40%、待派工單超過 2 小時無人接、技師接單率低於 50% |

**為什麼需要：** 沒有基準數據，儀表板做出來只是好看的圖表，不會幫你發現問題。告警閾值決定了系統何時通知管理員介入。這些數據也是 UAT 驗收的參考依據。

**允收標準：**
- 基準數據涵蓋至少 3 個月的歷史數據（或明確標注無數據）
- 目標 KPI 與合約允收標準一致
- 告警閾值至少定義 5 條規則

## 風險管理

| 風險 | 影響 | 預防措施 |
|:-----|:-----|:---------|
| 甲方技師沒空，0.1 領域知識延遲 | Phase 0 資料模型設計方向錯誤，ProblemCard Schema 與現實脫節 | PM 先用電話訪談 + 現有 LINE 對話截圖整理初版，再請技師驗證修正 |
| 歷史案例 < 200 筆 | AI 準確率無法達到 80% 合約要求 | 設定最低門檻 100 筆才開始 Phase 1 開發；不足的部分由 PM + 技師在 Phase 2 期間密集補充 |
| 產品手冊 PDF 品質差（掃描模糊） | RAG L2 層品質低落，檢索結果不準確 | 要求甲方優先提供電子版 PDF；掃描版使用 OCR 後人工校對關鍵段落 |
| LINE OA 帳號申請延遲 | 整個 V1.0 開發無法啟動 | Phase 0 第一天就確認帳號狀態，沒有的立刻申請（LINE 認證帳號審核約 5-10 工作天） |
| Google Cloud API 配額不足 | AI 模型呼叫被限流，影響開發與測試 | 確認 Gemini API 免費額度是否足夠開發測試用量；不足時提前申請付費方案 |
| 計價規則反覆修改（0.6） | Phase 6 報價引擎延遲 | 限定最多 2 輪修改，第 3 輪後凍結版本先開發，後續以系統設定方式調整 |
| 技師資料不齊全（0.5） | 派工引擎無法進行有效匹配測試 | 設定最低門檻：至少 10 位技師資料完整才開始 Phase 6 開發 |
